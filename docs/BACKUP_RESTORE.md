# DB 백업·복원 정책 (Backup & Restore Policy)

> 담당: 카드 12(배포·운영) 실행 전 정책 수립 — 작성: giyeop-cody (#3 #12)
> 대상: SQLite `app.db` (users, chat_logs)

## 1. 목표 (RPO/RTO)

| 지표 | 목표 | 근거 |
|------|------|------|
| RPO (손실 허용 시점) | **24시간** | 과제 서비스 특성상 일일 백업으로 충분, 채팅 로그는 재생성 불가하지만 평가 영향 미미 |
| RTO (복구 목표 시간) | **1시간** | SQLite 단일 파일 → 파일 복원 + 재시작이면 달성 가능 |

## 2. 백업 정책

### 무엇을 / 무엇을 제외
- ✅ 대상: `app.db` 단일 파일 (스키마+데이터 전부)
- ❌ 제외: `.env` — **시크릿은 백업 파일에 넣지 않는다** (백업 유출 = 키 유출). 시크릿은 배포 플랫폼의 시크릿 관리에만 존재

### 방법 — 온라인 백업 (핵심)
SQLite은 서버가 쓰는 중 파일 복사(`cp`)하면 **깨진 백업**이 될 수 있음 → 반드시 sqlite3의 온라인 백업 API 사용:

```bash
./scripts/backup_db.sh            # 실행 중에도 안전하게 백업
```

`scripts/backup_db.sh`가 하는 일:
1. `sqlite3 app.db ".backup 'backups/app_YYYYMMDD_HHMMSS.db'"` (무결성 보장)
2. `PRAGMA integrity_check`로 백업본 검증
3. 보관 세대 관리: **최근 7개만 유지** (자동 삭제)

### 주기
| 시점 | 행위 |
|------|------|
| 매일 1회 (배포 환경) | 스크립트 실행 (cron/플랫폼 스케줄러 — 카드 12가 배포 시 등록) |
| 큰 변경 전후 (마이그레이션·대량 시딩) | 수동 즉시 백업 |
| 제출 직전 (M3) | 최종 스냅샷 + 증빙 캡처 |

보관 원칙(3-2-1의 축약판): **최근 7세대, 원격(로컬 다운로드) 1세대 이상** — 배포 플랫폼 디스크가 날아가도 로컬 1개는 생존하도록 주간 1회 백업본 다운로드.

## 3. 복원 절차 (드릴 포함)

```bash
# 1) 서버 정지 (또는 유지보수 모드)
# 2) 현재 파일 보호
mv app.db app.db.broken
# 3) 백업본 복원
cp backups/app_20260907_120000.db app.db
# 4) 무결성 확인 후 재기동
sqlite3 app.db "PRAGMA integrity_check;"
uvicorn app.main:app --host 0.0.0.0
# 5) /health + 로그인/채팅 1회씩 검증
```

**복원 드릴**: 월 1회 + M2(Milestone)에서 1회 실시 → `docs/evidence/restore_drill_*.md`에 기록(날짜/소요시간/결과). RTO 1시간 달성 여부를 실측한다.

## 4. 실패 시나리오와 대응

| 시나리오 | 대응 |
|----------|------|
| 백업본 자체가 깨짐 | integrity_check 실패 세대는 버리고 이전 세대 — 7세대 보관 이유 |
| DB 파일 삭제/디스크 유실 | 로컬 보관본으로 복원 (RPO 24h 손실 감수) |
| 스키마 불일치(구 백업→신 코드) | 백업본을 띄운 후 마이그레이션 실행 — 현재는 create_all 기반이라 하위호환 유지 필요 시 문서화 |

## 5. 트레이드오프
- **매일 백업 vs 더 잦은 백업**: 채팅 로그 가치가 시간당 낮아 24h RPO 선택. 실서비스라면 WAL + 증분 복제 고려
- **파일 복사(cp) 금지의 이유**: 실행 중 복사는 페이지 불일치 위험 — 항상 `.backup` API 사용 (자동화로 실수 여지 제거)
