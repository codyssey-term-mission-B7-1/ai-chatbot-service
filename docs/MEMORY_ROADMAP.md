# 메모리·컨텍스트 전략 로드맵 (Stage 0 → 하이브리드 RAG)

> **본 문서의 위치**: 현재 서비스는 "같은 사용자의 **직전 5개 성공 Q/A 쌍** + 닉네임(시스템 프롬프트)"을 AI 문맥으로 쓴다(ADR-005, #122). 2026-09-12 코드 리뷰에서 "산업 표준 챗봇은 직전 창 + 벡터 DB 검색(RAG) + 요약 압축을 합쳐 프롬프트를 구성한다"는 지적이 있어, 그 방향과 단계별 실행 계획을 기록한다.
>
> **본 문서는 로드맵 기록이다 — 코드·행동 변경 없음.** 각 스테이지는 트리거 조건과 수락 기준을 통과할 때만 시작한다.

## 1. 현재 상태 (Stage 0) — 직전 5쌍 + 이름

```
POST /api/chat
  history = chat_logs.successful_context(user, 5)   # 성공만, 최신 5개 → 오래된 순
  system  = SYSTEM_PROMPT + "\n현재 대화 상대: {닉네임}님"   # 매 요청 항상
  messages = [system] + history(5쌍) + [현재 질문]
```

**운영 실측 (2026-09-12, 실 AI)**: 6개 코드워드(TANGO→HOTEL) 6턴 후 검증 질문 → AI가 "5개: DELTA, ECHO, FOXTROT, GOLF, HOTEL" + 닉네임 정확히 응답. 즉 AI가 실제로 받은 것은 **직전 5쌍(가장 오래된 TANGO 제외) + 이름**과 정확히 일치한다.

| 특성 | 평가 |
|---|---|
| 비용·실패모드 | 0 — 외부 의존·인덱스 불일치 없음 |
| 가시성 | **"보인 것 = AI가 본 것"** — /logs의 success 필터 5개가 AI 문맥과 동일 집합 |
| 예측 가능성 | 결정적(같은 DB 상태 → 같은 문맥), 회귀 테스트·평가에 유리 |

**한계 (성장 병목)**:

1. **5턴 밖은 증발** — 1,000턴 히스토리가 있어도 AI는 최근 5쌍만 봄
2. **의미 매칭 없음** — "지난주 DB 백업 얘기했잖아"가 창 안에 우연히 들어와야만 해결됨
3. **압축 없음** — 히스토리가 늘어도 문헌 예산은 항상 5쌍(중요 사실 누적 불가)
4. **망각·관리 없음** — 기록은 무한 누적(개인정보 표면이 선형 증가, 사용자 삭제 수단 부재)

## 2. 산업 표준 패턴 — 왜 "직전 N개만"이 아냐

OpenAI Memory · MemGPT/Letta · Mem0 · Zep 등 프로덕션 장기 기억 챗봇은 **사실상 수렴된 3축 구조**를 가진다:

```
 쓰기 경로 : 사용자 턴 → (1) 원문 기록(chat_logs)
                            → (2) 인덱싱(embedding 또는 FTS/지식구조)
                            → (3) 주기적 요약 (선택, Stage C)
 읽기 경로 : 현재 질문 → [직전 N쌍(원문)] + [검색 top-k(의미/키워드)]
               → 중복 제거 → 시간순 → 토큰 예산 할당 → messages
 망각      : TTL/감쇠 · 모순 시 최신 우선 · 사용자 요청 삭제
```

| 시스템 | 핵심 표현 | 특징 |
|---|---|---|
| OpenAI Memory | 원문 검색 + 요약 2축 | "conversation search"(유사 과거 대화) + "memory summary"(압축) |
| MemGPT/Letta | 메인 컨텍스트/외부 컨텍스트 | 프롬프트 안(근처) 밖(검색) 페이징, 자기 편집 메모리 |
| Mem0 | LLM 추출 사실 | 쓰기 시 LLM이 "사실"을 추출해 벡터 저장, add/update/delete 연산 |
| Zep(Graphiti) | 시간성 지식 그래프 | 관계·유효기간 추론(가장 무겁고 강력) |

**공통점**: 직전 창 **단독**으로 쓰는 시스템은 없다. 차이는 표현(원문 쌍 vs 사실 vs 그래프)과 쓰기 경로(직접 인덱싱 vs LLM 추출)뿐이며, **읽기에 의미/키워드 검색을 합치는 점**은 일치한다.

## 3. 로드맵 — 이 코드베이스 기준 3단계

### Stage A — SQLite FTS5 하이브리드 (새 인프라 0)

**목표**: 창 밖 회상을 키워드 수준에서 해결 — "직전 5쌍 + 유사 키워드 3쌍".

**설계**:
- `CREATE VIRTUAL TABLE chat_logs_fts USING fts5(question, answer, content='chat_logs', tokenize='trigram')` — trigram 토크나이저는 자막 분할 없이도 **한국어 부분일치**를 지원
- `save_log` 성공 시 인덱싱(동기, μs~ms). 삭제 시 FTS 행도 정리(외부 사용자 제거 CASCADE와 연결)
- 읽기: `successful_context(5)` 결과의 id를 제외하고 `MATCH`(질문에서 추출한 키워드) → `ORDER BY rank LIMIT k`
- 조립: 검색된 쌍은 **최근 5쌍보다 앞에, 시간순** 배치(대화 흐름 보존). 조립은 항상 "오래된 → 새로운"
- 설정: `context_retrieval_enabled`(기본 on) · `context_retrieval_top_k`(기본 3) — off 시 Stage 0과 **완전 동일**
- 관측: 검색된 id·rank를 request_id 로그에 기록 (request_id 추적 문법과 동일)

**비용/지연**: FTS 검색 ms 수준(로컬), API 비용 0, 인메모리 상태 0 → **단일 워커 전제와도 충돌 없음**

**리스크**:
- trigram 부분일치의 오탐(짧은 단어) → 키워드 최소 길이 필터 + rank 가중
- 프롬프트 팽창 → top_k + 토큰 예산 상한(기존 max_tokens 800은 출력 예산, 입력 예산은 Stage B에서 정식화)
- 인덱스/본체 불일치 → `content=` external content 테이블로 자동 동기 + 일관성 검증 테스트

**검증**:
- 단위: FTS 쿼리·조립 순서·중복 제거 / 통합: 5턴 밖 턴이 검색됨 / golden_set 확장: 창 밖 회상 케이스
- E2E 스모크 회귀(기존 7단계 영향 없음 확인)

**수락 기준**: ① golden 확장 케이스(창 밖 회상) 통과 ② p95 채팅 지연 +50ms 이내 ③ `context_retrieval_enabled=false` 시 Stage 0과 응답 동등(회귀 0)

**공수**: PR 1~2개 (스키마+쿼리+설정+테스트). **트리거: 팀 합의 시 (스케일 요구 없음)**

### Stage B — 벡터 RAG (진짜 의미 매칭)

**목표**: "지난주 DB 백업 어디까지 했지?" 수준의 **파라프레이징** 회상.

**전제**: Postgres 전환(`docs/POSTGRES_MIGRATION.md` — 이미 스키마/쿼리가 호환, Alembic 관리) → **pgvector**. (대안: Qdrant 등 독립 스토어 — Railway에서 별도 서비스 1개 더 돌리는 비용)

**구성**:
- `chat_memories` 테이블: `id, user_id, kind(pair|summary), text, embedding(vector), created_at, last_used_at, use_count, expires_at`
- 임베딩: 제공사 호환 `/embeddings`(기존 `AI_BASE_URL` 지원 여부 확인 → 미지원 시 별도 `EMBEDDING_*` 설정). 모델·차원 고정(예: 1024)
- **쓰기 경로 = 비동기**: `save_log` 성공 후 배치(스레드/큐). **채팅 응답을 절대 지연시키지 않음**. 실패 시 로그 + 스킵(메모리 누락은 치명적 아님 — 원문은 chat_logs에 항상 존재)
- **읽기 경로**: `embed(question)` → 사용자별 벡터 top-8 + 직전 5쌍 → **RRF(Reciprocal Rank Fusion)** 하이브리드 → 중복 제거 → 토큰 예산 → messages
- 제공사 장애 시: 임베딩 실패 → **검색 없이 직전 5쌍으로 degraded 동작**(Stage 0 수준, 응답은 200)

**비용/지연**: 턴당 임베딩 1회(입력 토큰만) + pgvector 검색(ms). 구체 비용은 제공사 단가로 산출 후 운영 승인

**검증**: golden_set v2 — **파라프레이징 질의**(동일 사실, 다른 표현) recall@k 측정. 쓰기 비동기의 순서/실패 격리 테스트. 제공사 장애 degraded 테스트

**수락 기준**: ① 파라프라이징 recall@5 ≥ 0.9(내부 golden) ② 채팅 p95에 쓰기 경로 영향 0(비동기 증명) ③ 제공사 장애 시 Stage 0 동등 동작

**공수**: PR 4~6개 (마이그레이션 · services/memory · 비동기 파이프라인 · 설정 · 테스트). **트리거: Postgres 전환 결정 또는 "장기 기억" 요구가 구체화된 시점**

### Stage C — 압축·망각 (메모리 정리)

**목표**: OpenAI Memory의 두 번째 축 — 요약으로 5쌍 이상의 사정을 담고, 개인정보 표면을 통제한다.

**구성**:
- **주기적 요약**: 사용자 히스토리가 N(예: 50)턴 초과 시 lazy, 또는 매일 배치 — 최근 50턴을 요약해 `kind=summary`로 저장
- 시스템 프롬프트: "메모리 요약: …"(예산 제한, 요약 1~2개)
- **모순 처리**: 최신 우선(새 요약/사실이 구 것을 대체)
- **망각**: `expires_at` 감쇠 + **사용자 요청 삭제**(개인정보) — `/logs` UX 확장: 대화 삭제 버튼 → 원문 + FTS + 벡터 인덱스 **동시** 삭제(단계별 CASCADE 계약)

**수락 기준**: ① 1,000턴 히스토리 사용자의 요약이 핵심 사실 보존(golden) ② 사용자 삭제 시 모든 인덱스에서 소거 검증(테스트)

**공수**: PR 2~3개. **트리거: 사용자당 히스토리가 50턴+로 일상화된 시점**

### 공통 과제 (모든 스테이지)

- **개인정보**: "사용자가 자신의 메모리를 볼 수 있고 지울 수 있다" — Stage 0의 `/logs`(전체 표시)는 좋은 출발점. 각 스테이지에서 **인덱스까지** 삭제 CASCADE
- **평가 하니스**: golden_set을 v2(창 밖 · 파라프라이징 · 모순)로 확장 — `scripts/golden_set` 체계를 재활용, CI 수동 실행 또는 운영 스크립트로
- **순서 원칙**: A는 독립적, B는 Postgres 전환 종속 → **A → (Postgres 전환) → B → C**
- **역행 가능**: 모든 스테이지는 `enabled` 플래그로 이전 단계로 퇴보 가능(데플레이어 아님)

## 4. 왜 지금은 Stage 0을 유지하는가

1. **미션 명세**가 "같은 사용자의 과거 성공 Q/A를 문맥으로 사용"으로 정의 — 5쌍 창은 명세의 **최소 정합 구현**이며 평가·운영 전제가 그 위에 세워져 있음
2. 현재 규모(수백 계정 미만, 단일 워커)에서 A/B의 이득(창 밖 회상)보다 **신규 실패모드**(인덱스 불일치, 제공사 의존, 프롬프트 팽창)의 유지보수 비용이 앞서면 안 됨
3. 따라서 **방향은 로드맵에 기록하고, 행동은 각 스테이지의 수락 기준을 통과할 때만 변경** — ADR-010
