## 2. 상세 규칙

### 2.1. 비밀번호 정책 (정확한 계약)
- **길이**: 8~64 Unicode 코드 포인트 **그리고** UTF-8 인코딩 72바이트 이하 (한글 25자=75바이트는 422).
- **공백 전용 거부**: 스페이스/개행/탭만으로 구성되면 422 (09-09 추가, PR #90).
- **초과 시 잘라서 해싱하지 않는다** — bcrypt 72바이트 절단 사양에 대한 방어(§ 의사결정 D-10).
- **저장**: 페퍼(HMAC-SHA256, 서버 비밀 PASSWORD_PEPPER) 사전 변환 → bcrypt(비밀번호별 무작위 솔트).
- **마이그레이션**: 페퍼 도입 전 계정은 다음 로그인 때 자동 재해싱. 관리자 API로 미전환 현황 조회 가능.

### 2.2. 세션 계약
- `SessionMiddleware` 서명 쿠키. 페이로드는 `user_id` + `email_fp`(지문 — 평문 email은 감사(#59)로 제거됨).
- 로그인 시 `iat`(발급 시각) 기록 → `session_revocations.revoked_before_epoch` 이하의 iat는 서명이 유효해도 거부(계정별 전면 폐기).
- 쿠키 속성: HttpOnly · SameSite=Lax · Max-Age=SESSION_MAX_AGE_HOURS(기본 24h, 상한 168h) · 운영 Secure.
- **세션-계정 바인딩**: user_id만 믿지 않고 이메일 지문 대조 — DB 재생성으로 id가 재할당돼도 stale 쿠키는 401 (이슈 #33 → PR #34).

### 2.3. 오류 응답 계약 (통일 포맷)

| 상황 | 상태 | error 코드 | 사용자 안내(UI) |
|---|---|---|---|
| 검증 실패 | 422 | (FastAPI detail 배열) | 필드별 메시지, textContent로만 표시 |
| 이메일 중복 | 409 | EMAIL_EXISTS | "이미 가입된 이메일이에요" |
| 비로그인 | 401 | UNAUTHORIZED | 로그인 페이지 유도(API) / 302(HTML) |
| 권한 없음 | 403 | FORBIDDEN | 관리자 전용 안내 |
| 로그인 잠금 | 429 | — + Retry-After | "잠시 후 다시 시도" |
| 채팅 한도 초과 | 429 | — + Retry-After | 분당 요청 안내 |
| AI 응답 형식 오류 | 502 | AI_ERROR | "AI 응답에 문제가 있어요" |
| AI 타임아웃 | 504 | AI_TIMEOUT | "AI 응답이 지연되고 있어요. 잠시 후 다시 시도해 주세요" |
| 발송 수단 없음(운영) | 503 | — | 메일 설정 안내 |

모든 응답에 `X-Request-ID` — 로그 이벤트·DB `chat_logs.request_id`와 연결되어 장애 추적선이 된다.

## 3. 채팅 파이프라인 계약

### 3.1. 처리 순서 (README §2와 동일)
**입력 검증 → 같은 사용자의 성공 Q/A 로딩(문맥) → AI 호출 → DB 저장 시도 → HTTP 응답**
- DB 저장 실패 시에도 사용자에게 응답은 전달되며 `chat_id=-1` 계약으로 구분한다 (기록 유실은 사용자 안내 없이 조용히 실패하지 않도록 로그 `db_save_fail` 기록).
- AI 호출 중에는 DB 커넥션을 **반납**한다(감사 #73 → PR #77) — 호출 지연이 커넥션 고갈로 번지지 않게.

### 3.2. AI 호출 시간·재시도 정책
- `AI_TIMEOUT_SEC`(기본 45초)은 **AI 호출 전체 예산**: 연결·읽기·추가 시도·대기를 모두 포함. DB/전체 HTTP 시간은 제외.
- **타임아웃은 재시도하지 않는다** — 느린 응답을 다시 기다리는 것은 예산 위반. 전송 오류·429·5xx만 `AI_MAX_RETRIES`(기본 1)회 추가 시도.
- 다른 4xx·malformed 응답은 즉시 AI_ERROR/502.
- 타임아웃 검증 방법: `AI_TIMEOUT_SEC=0.001` 강제 유발 → 서버 생존 + 504 + `ai_call_fail` 로그 캡처 (역할카드 06 완료 조건).

### 3.3. 문맥 구성 규칙
- 같은 사용자 **성공(status=success) Q/A만** 직전 `CONTEXT_TURNS`쌍, 오래된 순서로 messages에 user/assistant 교대 삽입.
- 0이면 비활성화, 상한 200(정책 상수 MAX_CONTEXT_TURNS). 시스템 프롬프트는 "이전 질문을 표현 그대로 따옴표 인용, 없는 내용 지어내지 않기"를 지시.
- UI 복원도 서버와 같은 `status=success&limit=N`을 쓴다 — 실패 로그가 50건 있어도 성공 문맥을 잃지 않는다 (PR #28).

## 5. 기능 명세 의사결정 기록

### D-10. 세션 인증 방식

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) 서명 쿠키(itsdangerous SessionMiddleware)** | 서버 저장소 불필요, 표준 미들웨어, 구현 짧음 | 페이로드가 클라이언트에 있어 **서버 측 폐기가 기본은 안 됨** → 별도 설계 필요 |
| (2) JWT (Authorization 헤더) | 무상태 확장성, 표준 | 브라우저 저장 위치 문제(localStorage XSS), 폐기는 쿠키보다 더 어려움, 과제 규모에 과설계 |
| (3) 서버 세션 저장(DB/메모리 세션 테이블) | 즉시 폐기 가능 | 요청마다 조회 비용, 세션 테이블 관리 코드 추가 |
| (4) OAuth/소셜 | 비밀번호 책임 회피 | 외부 심사·리다이렉트 → 15일 일정에 배포 병목, 과제 요구(자체 가입) 불일치 |

**최종 선택: (1)** — 이유: 단일 워커·소규모 사용자 전제에서 가장 단순하고 검증하기 쉽다. 단점(폐기 불가)은 **iat 기반 폐기 테이블**(FR-20)과 **세션-계정 바인딩**(§2.2)으로 보완 — "선택한 방식의 약점을 알고 그 약점을 명시적으로 메운다"는 원칙의 대표 사례. 실제로 감사(#55, #74)에서 지적된 수명·폐기 문제를 이 구조 안에서 해결했다.

### D-11. 비밀번호 저장 방식

| 선택지 | 장점 | 단점 |
|---|---|---|
| bcrypt | 널리 검증됨, 솔트 자동, passlib 표준 지원 | 72바이트 입력 절단 사양 |
| **bcrypt + 페퍼(HMAC-SHA256 사전 변환)** | DB 유출 시에도 페퍼 없으면 오프라인 대조 불가, 절단 문제도 우회(먼저 HMAC 출력으로 고정 길이) | 서버 비밀(PEPPER) 운영 관리 필요 — CD Secrets 게이트로 강제 |
| Argon2id | 최신 메모리 하드 함수 | passlib에서 별도 패키지(argon2-cffi), 검증·문서 자료 상대적으로 적음 |
| PBKDF2/SHA-256 | 표준 라이브러리만으로 가능 | GPU 공격에 약함 — 비밀번호 저장용으로는 설명 난처 |

**최종 선택: (2)** — 이유: bcrypt의 검증된 안전성을 유지하면서 "DB만 유출되는" 현실적 시나리오에 대한 방어를 얹는다. 72바이트 절단 문제를 HMAC 고정 출력으로 자연 해결하는 점도 결정적이었다. 운영 필수값으로 CD가 32자 이상 PEPPER를 사전 검증하고, 기존 계정은 로그인 시 자동 재해싱해 마이그레이션 비용을 0으로 만들었다(PR #90).

### D-12. 로그인·채팅 남용 방어 구현 위치

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) 프로세스 메모리 슬라이딩 윈도우** | 외부 의존 0, 코드 60줄 수준, 단일 워커에 정확히 동작 | 다중 워커·재시작 시 카운터 초기화 — 한계를 코드 주석·문서에 명시 |
| (2) DB 카운터 테이블 | 재시작에도 유지 | 모든 요청에 쓰기 발생, SQLite 쓰기 잠금 경합 |
| (3) Redis | 표준적 해법, 확장성 | 무료 플랜에서 또 하나의 서비스 운영 → 배포·Secrets 복잡도 증가 |
| (4) 미구현(과제 범위 밖) | 시간 절약 | 무차별 대입 무방비 — 감사 감점 명백 (#72, #73) |

**최종 선택: (1)** — 이유: Railway 단일 uvicorn 프로세스가 운영 형태이므로 (1)이 정확히 충분하다. 대신 클래스 주석에 "다중 워커·중앙 집계가 필요하면 Redis로 교체"라는 교체 경계를 명시해, 한계를 숨기지 않았다. 로그인 잠금(5회/15분)과 채팅 한도(10회/분)는 같은 클래스를 재사용한다.

### D-13. 입력 길이 기준

| 선택지 | 장점 | 단점 |
|---|---|---|

| (2) UTF-8 바이트 기준 | 전송량·DB 관점 직관 | 사용자 체감과 불일치(한글 1자=3바이트), 이모지 surrogate 처리 실수 위험 |
| (3) 길이 제한 없음 (AI 토큰에 맡김) | 구현 없음 | 남용·프롬프트 폭탄, 명세 요구(길이 1000 제한) 미충족 |

**최종 선택: (1), 단 비밀번호는 병행** — 이유: 화면 카운터·검증 메시지·서버 422가 같은 숫자를 말해야 UX가 성립한다. 단 bcrypt의 72바이트 절단은 바이트 세계의 사실이므로 비밀번호만 "코드 포인트 8~64 **그리고** 72바이트 이하"로 이중 규정했다. `MAX_QUESTION_LENGTH`는 설정값을 화면까지 전달해(감사 #53 정정, PR #63) 하드코딩 이중 관리를 없앴다.

### D-14. 오류 응답 포맷

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) HTTP 상태 + error 코드 + 안내 메시지** | 프론트 분기가 코드 단위로 정확, 문서화 쉬움 | FastAPI 기본 detail과 병존해 팀 컨벤션 필요 |
| (2) RFC 7807 problem+json | 표준 | 팀·평가 관점에서 남용, 필드 제약이 오히려 불편 |
| (3) 상태 코드만 | 단순 | 사용자 안내 문구가 프론트 하드코딩으로 흩어짐 |

**최종 선택: (1)** — 이유: AI_TIMEOUT(504)과 AI_ERROR(502)처럼 "같은 실패지만 안내가 다른" 케이스를 코드로 구분하는 것이 사용자 안내 품질의 핵심이었다. 프론트는 `errorText()`로 detail 배열·문자열을 정규화하고 항상 `textContent`로만 표시한다(회귀 #60의 교훈 반영).
