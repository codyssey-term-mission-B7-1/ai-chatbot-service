## 3. S1 로그인/회원가입 (mode 토글 단일 템플릿)

```
┌──────────────────────────┐
│   [회원가입 | 로그인] 탭      │
│  이메일  [____________]    │
│  비밀번호 [____________]    │
│  닉네임  [____________]    │ ← 회원가입 모드만
│  [        제출        ]   │
│  오류 메시지 영역(aria-live) │
└──────────────────────────┘
```

| 요소 | 규칙 |
|---|---|
| 이메일 | 형식 검증, 중복 409 → "이미 가입된 이메일이에요" |
| 비밀번호 | 8~64자·72바이트·공백전용 거부 — 위반 시 서버 422 메시지를 그대로 표시(바이트 초과 안내 포함) |
| 닉네임 | ≤20자, 공백 시 이메일 접두어 자동 |
| 제출 중 | 버튼 disabled로 중복 제출 방지 |
| 성공 | 채팅 화면(/)으로 이동 |

클라이언트 검증은 "빠른 피드백"일 뿐이고 **서버가 최종 계약** — 양쪽 메시지가 서로 불일치하지 않도록 서버 응답을 우선 표시한다.

## 4. S2 채팅 (서비스 핵심 화면)

```
┌──────────────────────────────────────────────┐
│  대화 창 (chat-window)                         │
│  ┌ user bubble ────────────┐ 09:14 KST        │
│  └─────────────────────────┘                  │
│  ┌ ai bubble ──────────────┐ 09:14 KST        │
│  └─────────────────────────┘                  │
│  ── 이전 대화 N개를 복원했어요 ── (구분선)          │
├──────────────────────────────────────────────┤
│ [textarea: 질문을 입력하세요 (최대 1000자)] [보내기] │
│                              123/1000 (카운터) │
└──────────────────────────────────────────────┘
```

| 동작 | 명세 |
|---|---|
| **Enter 전송 / Shift+Enter 줄바꿈** | keydown 핸들러. **IME 조합 중(`event.isComposing`) Enter는 전송하지 않음** — 한글 자모 확정 Enter가 전송으로 오인되는 것을 차단 (이슈 #29, 회귀 복구 #60/#61) |
| 전송 중 잠금 | sendBtn.disabled + "AI 응답 대기 중…" 로딩 버블 → 중복 전송 차단 |
| 글자 수 카운터 | 코드 포인트 기준, 서버 `MAX_QUESTION_LENGTH`와 동일 상한 표시 |
| 입력 자동 높이 조절 | rows=1 → 내용에 따라 확장 |
| 오류 표시 | 상태별 안내(§03 2.3 계약): 504 "AI 응답이 지연되고 있어요…", 429 "분당 요청 한도…", 502 "AI 응답에 문제…". **항상 textContent로만** (innerHTML 보간 금지 — #60 교훈) |
| 기록 복원 | 로드 시 GET /api/me/chats?status=success&limit=N → 서버가 문맥에 쓴 것과 같은 범위, KST 표기 (#87) |
| 타임스탬프 | 로컬 시각(KST) 표시, 기록 화면은 KST/UTC 병기 계약 (#87, #103) |
| 데모 배너 | ai_mode=demo일 때 "데모 응답" 고지 + 닫기 버튼 (#87) — 실AI/데모 혼동 방지 |

## 5. S3 내 대화 기록 / S4 관리자 조회

**S3 /logs**: 본인 대화만. 질문·응답·시각(KST/UTC 병기)·상태 목록, 성공/실패 상태 배지. 비로그인 302.

**S4 /admin/logs**: 부여된 관리자만. 전체 사용자 대화 조회 + 이메일/사용자 필터 + 사용자 삭제·해시 마이그레이션 현황(09-09 확장, PR #92). 일반 사용자는 403 — UI가 아니라 **서버가** 차단하며, 테스트(test_admin)로 고정.

## 8. 화면 명세 의사결정 기록

### D-15. 프론트엔드 구조

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) Jinja2 SSR + vanilla JS 분리(static/js/)** | 빌드 도구 0, 템플릿 자동 이스케이프로 XSS 기본 방어, FastAPI StaticFiles와 자연 결합 | 상태 관리 직접 구현(전송 잠금·복원 등) |
| (2) React/Vite SPA | 상태 관리·컴포넌트 재사용 | 빌드 체인·호스팅 분리 → 15일 일정에 배포 리스크, 과제 평가 관점 산출물 대비 과함 |
| (3) HTMX | 선언적, SSR과 궁합 | 학습 곡선·디버깅 도구가 팀에 익숙하지 않음, 채팅 스트리밍 아닌 폴링 구조와 어울림 |
| (4) 인라인 JS (HTML 내 script) | 파일 수 최소 | CSP 'self' 정책과 충돌, 테스트·재사용 불가 |

**최종 선택: (1)** — 이유: 화면이 7개·상호작용이 명확(폼 3종 + 채팅 1종)해 SPA의 이득이 빌드 비용을 못 넘는다. 결정적으로 **CSP 도입(#75) 시 인라인 JS가 전부 막히므로** JS를 static/js로 분리하는 구조가 보안 요구와 정확히 일치했다(회귀 #60 이후 `addEventListener` 방식으로 표준화).

### D-16. 시각 표기 (타임스탬프)

| 선택지 | 장점 | 단점 |
|---|---|---|
| UTC만 | 저장·표기 단일 체계 | 한국 사용자가 매번 9시간 보정 — 사용성 결함 |
| **(1) UI는 KST, 데이터/계약은 UTC** | 사용자 친화 + 내부 계약(UTC Z) 불변 | 두 체계의 경계를 문서로 고정해야 함 |
| (2) 브라우저 로캘 자동 | 국제화에 유리 | "어느 팀의 시각인지" 증빙 대조가 번거로움 |

**최종 선택: (1)** — 이유: DB·API는 UTC `Z` 계약을 유지하되(테스트 고정), 화면 표기는 KST로 통일하고 기록 화면은 KST/UTC를 병기해 증빙 대조까지 커버. 이 계약은 증거 스크립트 갱신(#103)으로 회귀 방지까지 붙였다.

### D-17. 오류 메시지 렌더링 (회귀 이슈에서 재확정)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) errorText() 정규화 → textContent 삽입** | 서버 detail이 배열이든 문자열이든 안전, XSS 여지 원천 차단 | HTML 강조(bold 등) 불가 |
| (2) innerHTML + `<strong>` 보간 | 시각적으로 예쁨 | 서버 문자열이 그대로 HTML이 됨 — #60에서 유입됐던 위험 패턴 |

**최종 선택: (1)** — 이유: #60에서 innerHTML 보간이 유입됐던 사례가 있다. 현재 detail은 배열이라 즉시 취약하진 않았지만, 401 등 문자열 detail 경로에서 곧바로 위험해지는 패턴이라 원천 차단을 택했다. 레이아웃 시프트 제거(오류 표시 공간 예약)는 #90에서 함께 처리했다.

### D-18. 다크모드 제공 방식

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) prefers-color-scheme 자동 + CSS 변수** | 설정 비용 최소, OS 설정 존중 | 사용자가 화면 내에서 강제 전환 불가 |
| (2) 토글 버튼 + localStorage | 사용자 제어 | 추가 상태·접근성 라벨 관리 |
| (3) 미지원 | 공수 0 | 어두운 환경 사용성·감점 요인 |

**최종 선택: (1)** — 이유: #87의 7종 개선 중 하나로, CSS 변수 체계를 이미 갖고 있어 비용이 가장 낮았다. 서비스가 로그인 필수 웹앱이라 "사용자별 테마 저장" 가치가 낮다는 판단도 근거.
