## ADR-001. 배포 플랫폍 ✅ → Railway

**배경** (D1 결정): 평가 조건이 "외부 네트워크에서 접속 가능한 URL 상시 가동". 팀은 서버 관리 경험이 얕고, DB 영속화와 GitHub 연동이 필요했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **Railway** | GitHub push → 자동 배포, Volume(SQLite 영속), 환경변수 대시보드, 무료/저가 플랜 | Free/Hobby에서 **아웃바운드 SMTP 차단**(후일 실측으로 발견), 빌더 자동감지 동작 변화(후일 #81) |
| Render | 무료 티어 유명 | 무료는 슬립(sleep)으로 콜드스타트 — 평가 시점 응답 지연 리스크, 디스크 영속 유료 |
| Cloudtype | 한국 서비스, 문서 한글 | 팀 사용 경험 부족, 커뮤니티 자료 적음 |
| AWS EC2 + 수동 운영 | 완전한 제어 | 서버 세팅·보안 패치·재시작 관리 전부 수작업 — 15일 과제에서 최악의 비용 |

**결정: Railway** — 이유: "GitHub 연동 CD + 파일 영속(Volume)"이라는 두 요건을 무료~소액으로 동시 충족하는 유일한 후보였다. 플랫폼 제약은 리스크로 등록하고 D5 조기 배포 원칙으로 조기 발견하려 했으나 실제로는 D11~D12에 두 건(#81 Railpack 시작 명령, #100 SMTP 차단)이 터졌고, 각각 Procfile 추가와 Resend HTTPS 전환(ADR-005)으로 해결. **교훈: "플랫폼 제약은 배포 전 실측으로 확인"이 M1 회고의 정식 교훈으로 채택됨.**

## ADR-002. AI 연동 방식 ✅ → OpenAI 호환 직접 HTTP (httpx.AsyncClient)

**배경**: 과제 제공 API는 네이토(OpenAI 호환). 키는 서버에서만 쓰고, 타임아웃 생존성이 채점 포인트.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **httpx.AsyncClient 직접 래퍼(AIClient)** | 요청·타임아웃·재시도·에러 매핑을 전부 우리 계약으로 통제, OpenAI 호환 어디든 BASE_URL 교체만으로 접속 | 요청/응답 파싱을 직접 책임 |
| openai 공식 SDK | 파싱 편의 | 네이토 등 제3자 호환 엔드포인트에서 버전 호환 이슈 가능, 타임아웃·재시도 정책이 SDK 내부 동작과 섞임 |
| 프론트에서 직접 AI 호출 | 서버 부하 없음 | **키가 브라우저에 노출 — 과제 명시 위반(#27 항목)이자 치명적 보안 결함** |
| LangChain 등 프레임워크 | 추상화 풍부 | 과제 요구는 단순 chat completions — 학습·디버깅 비용 대비 이득 없음 |

**결정: 직접 래퍼** — 이유: "전체 시간 예산·선별 재시도·에러 코드 매핑(502/504)"이라는 우리의 계약을 정확히 구현·검증하려면 통제권이 필요하다. `scripts/ai_check.py`(--require-real 시 키 없으면 종료 2)와 모의 OpenAI 서버(mock_openai_server.py)로 검증 체계를 갖췄다. 결과: 09-07 네이토 연동 PR(#43), 09-10 운영 real 모드 실측(latency 1.6~2.0초).

## ADR-003. AI 타임아웃·재시도 정책 ✅ (09-07 조정)

**배경**: 초기 기본값 10초는 실제 모델 응답(특히 문맥 포함 시)에 너무 짧아 504가 남발됐다(이슈 #41).

| 선택지 | 장점 | 단점 |
|---|---|---|
| **전체 예산 45초 + 타임아웃 무재시도 + 전송오류/429/5xx만 1회 추가 시도** | 사용자 대기 상한이 명확, 예산 위반 없음, 일시 오류만 회수 | 느린 모델에서 대기가 김 (Retry-After·안내 메시지로 완화) |
| 10초 고정 (초안) | 빠른 실패 | 실사용 504 과다 → #41로 개선 요청 발생 |
| 타임아웃도 재시도 | 성공률 증가 | 90초까지 대기 가능 — UX·서버 자원 양손해 |
| 무제한 대기 | 실패 없음 | 요청 스레드 점유, 생존성 채점 포인트 상실 |

**결정: 예산 모델(45초)** — 이유: `AI_TIMEOUT_SEC`이 "연결·읽기·추가 시도·대기 포함 전체 예산"이라는 정의를 문서와 테스트(test_ai_http_budget)로 고정하고, 타임아웃은 재시도하지 않는다. 변경은 코드 1곳(config 기본값)+문서 3곳(#42)으로 끝나도록 설계돼 있었던 점도 변경 비용을 낮췄다.

## ADR-004. 대화 문맥 전략 ✅ → 직전 N턴 성공 Q/A (CONTEXT_TURNS 0~200, 기본 5)

**배경**: "이전 대화를 기억하는 챗봇"이 과제의 심장(역할카드 07). 토큰 비용과 시연 명확성의 균형이 필요.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **직전 N쌍 Q/A (성공만)** | 구현·설명·검증 단순, 토큰 상한 예측 가능, 실패 로그가 섞여도 문맥 오염 없음 | 먼 과거는 참조 불가 |
| 전체 기록 주입 | 완전한 기억 | 토큰 비용 비선형 증가, 오래된 무관 대화가 응답 품질 저하 |
| 대화 요약 저장 | 비용 절감 | 요약 품질·지연 추가, "원문 인용" 시연이 어려워짐 |
| RAG(벡터 검색) | 장기 기억 | 임베딩·벡터 저장소 인프라 — 과제 범위 밖 |

**결정: N턴 방식** — 이유: 역할카드 07이 "직전 N개 Q/A 포함"을 지정하고, `build_context` 순수 함수로 단위 테스트가 가능하다. 추가 결정: ① **성공(status=success) Q/A만** 포함해 실패 응답이 문맥을 오염시키지 않게, ② UI 복원도 같은 `status=success&limit=N` 계약을 공유해 화면과 AI가 같은 기억을 보게(PR #28), ③ 12번째 요청의 프롬프트 문자량 실측 실험(scripts/experiment_context_turns.py, DEMO_CONTEXT.md)으로 비용 증거까지 확보.

## ADR-005. 이메일 발송 경로 ↻ SMTP → Resend HTTPS API (09-10 변경)

**배경**: 비밀번호 재설정(FR-05) 채택 시 발송 수단이 필요. 초기에는 Gmail SMTP(SMTP_SSL) 경로를 구현.

| 선택지 | 장점 | 단점 |
|---|---|---|
| Gmail SMTP | 무료, 표준 프로토콜 | **Railway Free/Hobby는 SMTP 아웃바운드(25/465/587/2525) 전면 차단** — 09-10 Shell 실측 `OSError: [Errno 101]`로 확인(이슈 #100), 앱 비밀번호 2단계 설정 번거로움 |
| **Resend HTTPS API (443)** | 모든 플랜에서 허용되는 포트, JSON API로 간단 | 외부 서비스 가입·키 관리, 도메인 인증 전 본인 이메일만 수신 |
| SendGrid 등 타 API | 동급 | 무료 한도·가입 절차 유사 — Resend가 가장 단순 |
| 콘솔 출력/링크 직접 노출 | 구현 0 | 보안상 말도 안 됨(토큰이 URL로 누구에게나), 운영 기능 불성립 |

**결정: Resend 우선 + SMTP 폴백 유지** — 이유: `RESEND_API_KEY` 설정 시 Resend, 미설정 시 기존 SMTP(로컬 개발·Pro 대비), 둘 다 없으면 기존 동작(개발=로그 출력, 운영=503). SMTP 코드를 버리지 않은 이유: 로컬 fake 테스트 10건이 무수정으로 통과해 회귀 안전망이 유지됐기 때문(PR #101, 단위테스트 7건 추가, 전체 205 passed). **교훈: 플랫폼 제약은 "설정 문제가 아닌지" 먼저 Shell에서 격리 실측하고(Errno 101), 코드 변경은 우선순위 폴백 구조로 최소화한다.**

## ADR-006. 브랜치 전략·머지 규칙 ✅ → main ← develop ← feature, Merge commit 전용

**배경** (역할카드 02, D1~D2): 과제 요구 "브랜치 전략 + 팀원별 유의미한 커밋 10회+".

| 선택지 | 장점 | 단점 |
|---|---|---|
| **main/develop/feature 3단 + PR 필수 + Merge commit만** | 운영(main)·통합(develop) 분리로 배포 스냅샷이 항상 의미 있음, 개인 커밋이 이력에 그대로 남음 | 머지 커밋이 많아 이력이 복잡, develop 동기화 관리 필요 |
| GitHub Flow (main+feature만) | 단순 | 배포 커밋과 실험 커밋이 섞여 "배포 가능 시점" 식별이 어려움 |
| Trunk-based | 통합 충돌 최소 | 짧은 수명 브랜치 문화가 필요 — 커밋 10회 증빙 요구와 상충 |
| Squash 머지 허용 | 이력 깔끔 | **PR 안의 커밋 N개가 1개로 소멸 → 개인별 커밋 수 증빙 자체가 사라짐** |

**결정: 3단 git-flow 경량 + Squash 금지** — 이유: "커밋 10회" 채점을 머지 시점에 지우지 않는 것이 최우선. 룰셋(`allowed_merge_methods: ["merge"]`, 필수 승인 1, 마지막 push 셀프승인 차단, stale review 해제, 스레드 해결 강제, non_fast_forward/deletion 차단, bypass 없음)을 09-05 적용(#16)하고 저장소 설정으로도 Squash 버튼을 제거해 이중 안전장치를 뒀다(docs/git-rules.md 증빙). 실제 효과: 주간 감사가 `shortlog --no-merges`만으로 가능했고 1주차 0커밋 문제(#45)를 조기 발견했다.

## ADR-007. CI/CD 게이트 구성 ✅

| 선택지 | 장점 | 단점 |
|---|---|---|
| **CI: ruff+black+isort+pytest / CD: 테스트→Secrets 검증→변수 동기화→배포→헬스→스모크** | 스타일·동작·운영 3계층 전부 기계 검증, Secrets 누락 시 "성공으로 표시하지 않고 실패 중단" | 로컬과 CI 포맷 차이로 잦은 재푸시 (black 후속 커밋 발생 — 관행으로 보완) |
| lint만 (테스트 없음) | 빠름 | 회귀를 못 잡음 — #60 사례가 보여주듯 테스트가 없는 영역은 CI로도 못 잡음 |
| 수동 검증 (CI 없음) | 설정 비용 0 | 증빙(녹색 배지·실행 기록) 자체가 채점 요건 |

**결정: 전체 게이트** — 이유: CI 배지·실행 기록이 평가 증빙이고, "CD는 필수 Secrets 없으면 실패"라는 원칙이 "가짜 성공"을 막는 유일한 장치다. CD 게이트 순서는 운영 URL 게시(#83)와 직결됐다.

## ADR-008. 테스트 전략 ✅ → 단위+통합 중심, E2E/브라우저는 선택 증빙

| 선택지 | 장점 | 단점 |
|---|---|---|
| **pytest 단위(스키마·정책·순수함수)+통합(TestClient 실제 흐름) 205건** | 빠른 피드백, CI 게이트 가능, 계약별 회귀 고정 | 프론트 JS·실제 브라우저 렌더링은 미커버 |
| Playwright E2E 필수화 | 실제 화면 검증 | 실행 시간·인프라 비용이 CI마다 발생, 유지보수 부담 |
| 수동 테스트만 | 공수 최소 | #60이 증명한 대로 회귀를 문서로만 막을 수 없음 |

**결정: pytest 중심 + 브라우저 캡처는 스크립트(선택 실행)** — 이유: 백엔드 계약이 과제 채점의 본체다. 프론트 회귀는 ① `test_frontend_contract`(정적 계약 검사)로 최소 방어를 두고 ② Playwright 캡처 스크립트(capture_local_evidence.py)는 증빙 생성용으로 분리했다. 한계 인정: #60 같은 JS 회귀는 CI가 못 잡는다는 사실을 이슈 본문에 명시하고 "머지 직전 develop 재병합 후 삭제 라인 diff 확인"을 PR 절차에 추가했다.

## ADR-009. 프론트 JS 난독화 ❌→✅ (2026-09-12, CD 빌드 시에만)

**배경**: 원 결정(OBFUSCATION.md, 2026-08-30)은 "난독화 미적용" — 평가 가독성·협업 효율을 두고 시크릿은 서버만 가진다는 구조로 보호했다. 2026-09-12 운영 측 요청으로 "실서비스에 올라가는 JS가 그대로 노출된다"는 점을 완화할 것을 요구받아 재심사했다.

| 선택지 | 장점 | 단점·비용 |
|---|---|---|
| **(1) CD 빌드 시 난독화 (`tools/js-build`)** | 저장소 소스는 가독 유지(평가·협업·디버깅), 배포 산출물만 보호, seed 고정으로 재현 가능한 빌드, CI/CD 검증 게이트 | CD에 node 빌드 스텝 추가, 장애 디버깅은 소스 대조 필요 |
| (2) 커밋 시 난독화 | 빌드 스텝 0 | 소스 가독성 상실 — MIT 공개 정책·평가 가독성과 충돌, 팀 디버깅 저해(원 결정을 완전히 번복) |
| (3) 현상 유지(미적용) | 단순 | 운영 UI 로직·API 구조 힌트가 그대로 가독 —이번 요청이 해결하려는 리스크 |

**결정: (1)** — 이유: "소스는 가독, 산출물은 보호"는 원 결정의 취지(가독성)와 신규 요구(산출물 보호)를 동시에 충족한다.

- 도구: `tools/js-build/obfuscate.mjs` (javascript-obfuscator 4.x) — compact, controlFlowFlattening(0.5), stringArray+base64(0.9), splitStrings, unicodeEscapeSequence. `deadCodeInjection`/`debugProtection`/`selfDefending`은 의도적으로 비활성(UI 스크립트 특성·데모 서비스).
- **필수 전제**: `renameGlobals=false` + `transformObjectKeys=false` — `form-utils.js`가 `window.FormUtils`를 공개하고 `auth.js`·`chat.js`·`password-reset.js`가 참조하는 파일 간 계약이다. CI `js-build`가 `node --check` + FormUtils 계약 **런타임** 검증으로 보장한다.
- 검증: CI `js-build`(산출물 문법·계약) + CD 난독화 스텝(배포 전 in-place) + CD "JS 난독화 배포 검증"(배포 후 소스 주석 부재 + 문법). 로컬 Playwright 14체크·페이지 에러 0건으로 기능 동등 확인(2026-09-12).
- 한계: 난독화는 **장벽이지 암호가 아니다** — "난독화로 시크릿을 숨긴다"는 구조는 원 정책 원칙대로 금지(시크릿은 서버만).

## ADR-010. 메모리·컨텍스트 전략 — 하이브리드 RAG 로드맵 (2026-09-13, 행동 변경 없음)

**배경**: 2026-09-12 코드 리뷰 + 운영 실측(코드워드 6턴 테스트)으로 현재 "직전 5개 성공 쌍 + 닉네임(매 요청 시스템 프롬프트)"(ADR-005, #122)이 정확히 작동함을 확인했다. 리뷰 과정에서 "산업 표준 챗봇은 직전 창 단독이 아니라 **직전 N개 + 벡터 DB 유사 기록(RAG) + 대화 요약**을 합쳐 프롬프트를 구성한다"(OpenAI Memory, MemGPT/Letta, Mem0, Zep 등)는 지적이 있어 방향을 결정한다.

| 선택지 | 장점 | 단점·비용 |
|---|---|---|
| **(1) 하이브리드(직전 창 + 검색 + 압축) 로드맵 채택, 단계별 실행** | 산업 표준 방향, 전체 히스토리 회상, 단계가 작고 역행 가능(FTS5 → pgvector → 압축), 각 단계에 트리거·수락 기준 | 신규 실패모드(인덱스 불일치, 임베딩 제공사 의존, 프롬프트 팽창) — 단계별로 통제 |
| (2) Stage 0(5쌍 창) 유지 | 비용·실패모드 0, "보인 것 = AI가 본 것" 가시성, 명세 최소 정합 구현 | 5턴 밖 증발, 의미 매칭 없음, 요약·망각 부재 |
| (3) 바로 완전 벡터 RAG | 중간 단계 생략 | Postgres 전환 전제 + 임베딩 제공사 의존을 현재 규모에서 즉시 부담 — 비용 대비 효과 낮음 |

**결정: (1)** — 이유: 5쌍 창은 미션 명세의 최소 정합 구현으로서 현재(평가·운영 전제)에선 여전히 유효하지만, 성장 방향은 산업 표준과 일치하는 하이브리드다. 중간 단계(Stage A: SQLite FTS5)가 새 인프라 0으로 가장 큰 이득(창 밖 회상)을 주므로 1순위로 두고, 각 스테이지는 **트리거 조건 + 수락 기준**을 통과할 때만 시작하며 `enabled` 플래그로 역행 가능하게 설계한다.

- 로드맵 전문: [docs/MEMORY_ROADMAP.md](../MEMORY_ROADMAP.md) — Stage A(FTS5, 새 인프라 0) → Stage B(pgvector RAG, Postgres 전환 종속) → Stage C(요약·망각)
- 2026-09-13 기준 **코드·행동 변경 없음** — 향후 Stage A 시작 시 본 ADR을 ↻으로 갱신

## ADR-011. 대화 스레드(새 채팅) — 컨텍스트를 대화 단위로 분리 (2026-09-13)

**배경**: 사용자가 한 화면에서 여러 주제를 계속 이어 묻다 보면, "최근 5쌍" 문맥에 이전 주제 질문이 섞여 새 주제 답변의 정확도가 떨어진다(#125 이후 운영 피드백). "채팅 초기화"는 기록을 지우는 파괴적 옵션이라, **대화(스레드)를 여러 개 갖고 서로의 문맥을 격리**하는 방식으로 채택했다. MEMORY_ROADMAP(ADR-010)의 Stage A(FTS5)와는 무관하다 — 검색·요약이 아니라 **문맥 경계의 사용자 제어** 문제다.

| 선택지 | 장점 | 단점·비용 |
|---|---|---|
| **(1) 스레드 분할** — `threads` 테이블 + `chat_logs.thread_id`, 문맥을 스레드 스코핑 | 기록 보존(삭제 선택권은 사용자), 주제별 문맥 순수, UI가 대화 목록으로 전환/복귀 제공, Stage A~C와 정직교차(스레드 내·외 둘 다 동작) | 스키마+마이그레이션(레거시 백필), API 3개, UI/JS 변경 |
| (2) 채팅 초기화(기록 삭제) | 구현 최소 | 기록 영구 소실 — "새 주제" 의도와 달리 이전 대화 접근 불가, 되돌리기 없음 |
| (3) 유지(사용자 전체 5쌍) | 변경 0 | 주제 섞임 문제 지속 — 이번 요청이 해결하려는 문제 자체 |

**결정: (1)** — 실행 확정 사항:

- **스키마**: `threads(id, user_id, title, created_at, updated_at)`, `chat_logs.thread_id`(FK, ON DELETE CASCADE, index). alembic `c7e4a9b21d05` — 기존 사용자당 **`기본 대화` 스레드 1개 백필 + 기존 기록 전부 그 스레드에 귀속**.
- **기본 대화** = 가장 오래된(id 최소) 스레드. `thread_id` 미전달 채팅은 `resolve_default_thread`로 해제되며, **없으면 '기본 대화'로 생성하고 thread_id=NULL인 레거시 기록을 이 스레드에 레이지 백필**한다(운영은 마이그레이션이 이미 백필 → 0행 갱신).
- **문맥 경계**: `successful_context`는 **스레드 단위**(스레드 내 직전 N개 성공 Q/A). "보인 것 = AI가 본 것" 불변식은 스레드 안에 유지 — UI 복원도 같은 `thread_id` 필터.
- **제목**: 기본 대화는 고정 '기본 대화'. 그 외 스레드는 첫 질문에서 자동 생성(공백 압축, 코드포인트 20자 — policies 상수). 이후 제목은 불변.
- **삭제**: `DELETE /api/threads/{id}` — 그 스레드의 기록도 CASCADE로 함께 삭제(개인정보 자기결정권, MEMORY_ROADMAP 공통 과제 "사용자가 지울 수 있다"의 첫 수단). 남의 스레드는 404.
- **상한**: 사용자당 `MAX_THREADS_PER_USER`(기본 100) — 초과 409.
- **오류**: 타인·부존재 `thread_id` 채팅은 **AI 호출 전** 404(비용 방어 + 타인 대화 존재 은닉 — 존재 여부를 404/403으로 노출하지 않음).
- **로깅**: `thread_created`/`thread_deleted` 이벤트 등록, `ai_call_start`에 `thread_id` 필드(LOGGING.md 30종).
- **검증**: 통합 14 + 마이그레이션 백필 1 + e2e_smoke ⑧~⑩ + 로컬 Playwright 8단계(생성·자동제목·전환·삭제·복귀, 페이지 에러 0). 277 passed, 커버리지 95%.

**한계**: 스레드 수 100개 상한, 제목 20자 자동 생성(수동 변경 없음), 기본 대화는 다시 만들 수 없는 "0번째" 대화(삭제 후 남은 것이 기본). 검색 기반 회상(창 밖)은 여전히 Stage A 과제.

## ADR-012. 프론트엔드 구조 ✅ → Jinja2 SSR + Vanilla JS (static/js/)

**배경**: 화면 7종(로그인·회원가입·비밀번호 찾기·재설정·채팅·기록·관리자)에 대한 프론트엔드 기술 스택 결정. 15일 일정 안에서 배포 리스크 없이 완성해야 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) Jinja2 SSR + Vanilla JS 분리(`static/js/`)** | 빌드 도구 0, 템플릿 자동 이스케이프로 XSS 기본 방어, FastAPI `StaticFiles`와 자연 결합, CSP `script-src 'self'` 호환 | 상태 관리 직접 구현(전송 잠금·복원 등), JS 회귀를 CI가 못 잡음 |
| (2) React/Vite SPA | 상태 관리·컴포넌트 재사용·생태계 | 빌드 체인(Node.js) 추가, 호스팅 분리 또는 리버스 프록시 필요 → 15일 일정에 배포 리스크, 과제 평가 관점 산출물 대비 과잉 |
| (3) HTMX | 선언적, SSR과 궁합 좋음 | 학습 곡선·디버깅 도구가 팀에 익숙하지 않음, 채팅(스트리밍 아닌 폴링) 구조와 어울림 적음 |
| (4) 인라인 JS (HTML 내 `<script>`) | 파일 수 최소 | CSP `script-src 'self'` 정책과 충돌(#75), 테스트·재사용 불가 |

**결정: (1)** — 이유 3가지:

1. **화면 규모**: 페이지 7개, 상호작용은 폼 3종(로그인·회원가입·비밀번호 재설정) + 채팅 1종. SPA의 상태 관리·컴포넌트 재사용 이득이 빌드 체인 학습·배포 복잡도를 넘지 못한다.
2. **CSP 보안 정책과 정확히 일치**: 이슈 #75에서 `Content-Security-Policy` 도입 시 인라인 JS·HTML 속성 이벤트(`onclick` 등)가 전부 차단된다. JS를 `static/js/*.js` 파일로 분리 + `addEventListener` 방식으로 표준화하는 구조가 CSP 요구와 자연스럽게 일치.
3. **XSS 기본 방어**: Jinja2의 `{{ }}` 자동 이스케이프가 서버에서 내려오는 문자열(AI 응답·에러 메시지)의 HTML 렌더링 시 XSS를 기본 차단. 회귀 #60에서 `innerHTML` 보간 패턴이 유입됐을 때 `textContent` 전용으로 전환.

**트레이드오프와 보완**:
- JS 회귀는 CI가 못 잡음 → `test_frontend_contract`(정적 계약 검사: 인라인 핸들러 부재·필수 DOM 요소 존재) + Playwright 캡처 스크립트로 보완.
- 상태 관리 직접 구현 → `form-utils.js` 공용 모듈로 전송 잠금·에러 표시·검증 로직을 공유.
- 난독화는 CD 빌드 시에만 적용(ADR-009) — 소스 가독성 유지, 배포 산출물만 보호.

**현재 JS 파일 구조**:
```
static/js/
├── form-utils.js      # 공용: 폼 전송 잠금·에러 정규화·검증
├── auth.js            # 로그인·회원가입 탭 전환 + 폼 제출
├── chat.js            # 채팅: 전송·복원·문맥·스레드 전환
├── sidebar.js         # 사이드바: 드로어·접기·히스테리시스
├── theme.js           # 다크/라이트 토글
├── theme-init.js      # 페인트 전 테마 적용(깜빡임 방지)
├── logout.js          # 로그아웃 CSRF 방어
├── password-reset.js  # 비밀번호 재설정 폼
└── admin-logs.js      # 관리자 로그 조회 필터·페이지네이션
```

## ADR-013. 인증 방식 ✅ → 서버 사이드 세션 (Starlette SessionMiddleware + iat 폐기)

**배경**: 로그인 후 인증 상태 유지 수단 결정. 과제는 \"세션 기반 인증\"을 전제로 하고, 쿠키 위조·탈취·세션 하이재킹 대응이 채점 포인트다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) 서버 사이드 세션 (서명 쿠키 + DB 폐기 테이블)** | 구현 단순, 서버가 세션 무효화 통제 가능, 쿠키에 민감정보 없음(user_id+지문만) | 서버가 세션 상태를 알아야 폐기 가능(DB 대조), 다중 인스턴스 간 세션 공유 미지원(현재 단일 인스턴스) |
| (2) JWT (stateless) | 서버 저장소 불필요, 다중 인스턴스 자연 확장, API·모바일 친화적 | **서버 측 강제 무효화 불가**(만료까지 대기), 토큰 탈취 시 대응이 제한적, 리프레시 토큰 추가 시 세션과 동등한 복잡도 |
| (3) 서버 사이드 세션 (Redis 저장) | 세션 공유·강제 만료·실시간 통계 | Redis 인프라 추가(운영·비용·장애면 증가), 15일 과제의 단일 인스턴스에 과잉 |

**결정: (1)** — 이유:

1. **세션 무효화가 채점 포인트**: 비밀번호 재설정·계정 삭제 시 \"기존 세션 즉시 무효화\"가 필수 요구사항. JWT는 만료 전 강제 무효화가 구조적으로 불가능(블랙리스트 도입 시 Redis가 다시 필요해져 (3)과 동등).
2. **단일 인스턴스**: Railway Free/Hobby 1개 인스턴스에서 세션 공유 불필요 — 서버가 상태를 몰라도 쿠키 서명만으로 인증이 성립.
3. **쿠키 위조 방어**: `SESSION_SECRET` 품질 게이트(운영에서 32자 미만·기본값 거부, #54) + `Secure` + `HttpOnly` + `SameSite=Lax`로 방어층 구성.

### 현재 구현 구조

```
┌─────────────┐    서명 쿠키 (HMAC)    ┌──────────────────┐
│  브라우저     │ ──────────────────────→ │  Starlette        │
│             │ ←────────────────────── │  SessionMiddleware │
└─────────────┘   {user_id, email_fp,  └────────┬─────────┘
                     iat}                        │
                                                 ▼
                                       ┌──────────────────┐
                                       │  get_current_user │
                                       │  - 서명 검증       │
                                       │  - email_fp 대조   │
                                       │  - iat 폐기 대조   │
                                       └────────┬─────────┘
                                                │
                                                ▼
                                       ┌──────────────────┐
                                       │  session_revocations│
                                       │  (user_id, epoch)  │
                                       └──────────────────┘
```

- **쿠키 페이로드**: `user_id`(int), `email_fp`(이메일 HMAC 지문), `iat`(발급 epoch 초). email 평문 제거(#59).
- **폐기 메커니즘**: `session_revocations` 테이블의 `revoked_before_epoch` 이하 iat을 가진 세션은 거부. 비밀번호 재설정·계정 삭제·CLI(`scripts/revoke_sessions.py`)에서 폐기 트리거.
- **쿠키 수명**: 기본 24시간(`SESSION_MAX_AGE_HOURS`, 1~168h 설정 가능).

### JWT로 변경하려면?

현재 세션 → JWT 전환에 필요한 변경 사항:

| 영역 | 변경 내용 | 예상 공수 |
|---|---|---|
| **인증 미들웨어** | `SessionMiddleware` 제거 → JWT 검증 미들웨어 직접 구현(`Authorization: Bearer` 또는 쿠키) | 1일 |
| **토큰 발급** | 로그인 시 access_token(JWT, 15~30분) + refresh_token(서명 쿠키, 7일) 발급 | 0.5일 |
| **토큰 갱신** | `POST /api/auth/refresh` 엔드포인트 — refresh_token 검증 → 새 access_token 발급 | 0.5일 |
| **강제 무효화** | **JWT 블랙리스트**(Redis SET: `jti` 저장, TTL=토큰 만료) 도입 필수 — 없으면 비밀번호 재설정 시 기존 토큰이 만료까지 유효 | 1일 + Redis 인프라 |
| **프론트엔드** | 모든 `fetch` 호출에 `Authorization: Bearer` 헤더 주입, 401 시 refresh 자동 재시도 로직 | 1일 |
| **테스트** | 세션 기반 테스트 30+건 전면 수정 — 토큰 발급·검증·갱신·만료 시나리오 추가 | 1일 |
| **문서** | API.md·OPERATIONS.md·ADR-013 갱신 | 0.5일 |

**총 예상**: 약 **5.5일** + Redis 인프라. 가장 큰 비용은 강제 무효화(블랙리스트)와 기존 테스트 전면 수정.

**결론**: 현재 단일 인스턴스·24시간 세션 수명에서는 세션 방식이 더 단순하고 안전하다. JWT 전환은 **다중 인스턴스 배포** 또는 **모바일 앱/API 클라이언트** 도입 시점에 재검토한다.

### 100명 동시 접속 시 세션 관리 (확장 시나리오)

현재 구조는 **단일 인스턴스 + 서명 쿠키**이므로, 실제로 서버가 세션 데이터를 저장하지 않는다 — 쿠키 자체에 `user_id`+`email_fp`+`iat`이 HMAC 서명과 함께 들어 있어, 요청마다 서명 검증만으로 인증이 완료된다. 따라서:

| 시나리오 | 서버 부하 | 설명 |
|---|---|---|
| **현재 (단일 인스턴스)** | ✅ 문제 없음 | 100명이든 1000명이든 서명 검증은 O(1) — CPU 바운드이며 DB 조회는 `session_revocations` 대조 1회(캐시 가능) |
| **다중 인스턴스 (수평 확장)** | ✅ 세션 공유 불필요 | 서명 쿠키는 stateless — 모든 인스턴스가 같은 `SESSION_SECRET`만 공유하면 인증 가능. **Redis 없이도 확장 가능** |
| **강제 무효화 성능** | ⚠️ DB 조회 발생 | 매 요청 `session_revocations` 테이블 대조 — 100명 동시 접속 시 100회 SELECT. SQLite는 동시 쓰기 락이 병목이지만 읽기는 문제 없음. Postgres 전환 시 완전히 해소 |

**Redis가 필요한 시점**:
- **JWT 블랙리스트**: JWT로 전환하면 강제 무효화에 Redis SET(`jti` 저장)이 필수
- **실시간 세션 통계**: \"현재 활성 사용자 N명\" 대시보드 — 서버가 세션을 추적하지 않으므로 Redis에 세션 등록
- **rate limit 공유**: 현재는 인메모리라 다중 인스턴스 시 중복 카운트 — Redis로 공유 필요
- **Pub/Sub**: WebSocket 기반 실시간 기능 도입 시

**현재 100명 동시 접속에 대한 결론**: Redis 없이 처리 가능하다. 서명 쿠키 방식의 가장 큰 장점이 이것 — 서버가 세션 상태를 저장하지 않으므로, 인스턴스 수와 무관하게 인증이 동작한다. Redis는 JWT 전환·실시간 통계·rate limit 공유 등 **추가 기능**이 필요할 때 도입한다.
