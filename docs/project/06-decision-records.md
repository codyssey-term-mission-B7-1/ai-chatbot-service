## ADR-001. 배포 플랫폍 ✅ → Railway

**배경** (D1 결정): 평가 조건이 "외부 네트워크에서 접속 가능한 URL 상시 가동". 팀은 서버 관리 경험이 얕고, DB 영속화와 GitHub 연동이 필요했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **Railway** | GitHub push → 자동 배포, Volume(SQLite 영속), 환경변수 대시보드, 무료/저가 플랜 | Free/Hobby에서 **아웃바운드 SMTP 차단**(후일 실측으로 발견), 빌더 자동감지 동작 변화(후일 #81) |
| Render | 무료 티어 유명 | 무료는 슬립(sleep)으로 콜드스타트 — 평가 시점 응답 지연 리스크, 디스크 영속 유료 |
| Cloudtype | 한국 서비스, 문서 한글 | 팀 사용 경험 부족, 커뮤니티 자료 적음 |
| AWS EC2 + 수동 운영 | 완전한 제어 | 서버 세팅·보안 패치·재시작 관리 전부 수작업 — 15일 과제에서 최악의 비용 |

**결정: Railway** — 이유: "GitHub 연동 CD + 파일 영속(Volume)"이라는 두 요건을 무료~소액으로 동시 충족하는 유일한 후보였다. 플랫폼 제약은 리스크로 등록하고 D5 조기 배포 원칙으로 조기 발견하려 했으나 실제로는 D11~D12에 두 건(#81 Railpack 시작 명령, #100 SMTP 차단)이 터졌고, 각각 Procfile 추가와 Resend HTTPS 전환(ADR-005)으로 해결. **교훈: "플랫폼 제약은 배포 전 실측으로 확인"이 M1 회고의 정식 교훈으로 채택됨.**

## ADR-002. AI 연동 방식 ✅ → OpenAI 호환 직접 HTTP (httpx.AsyncClient)

**배경**: 과제 제공 API는 네이토(OpenAI 호환). 키는 서버에서만 쓰고, 타임아웃 생존성이 채점 포인트.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **httpx.AsyncClient 직접 래퍼(AIClient)** | 요청·타임아웃·재시도·에러 매핑을 전부 우리 계약으로 통제, OpenAI 호환 어디든 BASE_URL 교체만으로 접속 | 요청/응답 파싱을 직접 책임 |
| openai 공식 SDK | 파싱 편의 | 네이토 등 제3자 호환 엔드포인트에서 버전 호환 이슈 가능, 타임아웃·재시도 정책이 SDK 내부 동작과 섞임 |
| 프론트에서 직접 AI 호출 | 서버 부하 없음 | **키가 브라우저에 노출 — 과제 명시 위반(#27 항목)이자 치명적 보안 결함** |
| LangChain 등 프레임워크 | 추상화 풍부 | 과제 요구는 단순 chat completions — 학습·디버깅 비용 대비 이득 없음 |

**결정: 직접 래퍼** — 이유: "전체 시간 예산·선별 재시도·에러 코드 매핑(502/504)"이라는 우리의 계약을 정확히 구현·검증하려면 통제권이 필요하다. `scripts/ai_check.py`(--require-real 시 키 없으면 종료 2)와 모의 OpenAI 서버(mock_openai_server.py)로 검증 체계를 갖췄다. 결과: 09-07 네이토 연동 PR(#43), 09-10 운영 real 모드 실측(latency 1.6~2.0초).

## ADR-003. AI 타임아웃·재시도 정책 ✅ (09-07 조정)

**배경**: 초기 기본값 10초는 실제 모델 응답(특히 문맥 포함 시)에 너무 짧아 504가 남발됐다(이슈 #41).

| 선택지 | 장점 | 단점 |
|---|---|---|
| **전체 예산 45초 + 타임아웃 무재시도 + 전송오류/429/5xx만 1회 추가 시도** | 사용자 대기 상한이 명확, 예산 위반 없음, 일시 오류만 회수 | 느린 모델에서 대기가 김 (Retry-After·안내 메시지로 완화) |
| 10초 고정 (초안) | 빠른 실패 | 실사용 504 과다 → #41로 개선 요청 발생 |
| 타임아웃도 재시도 | 성공률 증가 | 90초까지 대기 가능 — UX·서버 자원 양손해 |
| 무제한 대기 | 실패 없음 | 요청 스레드 점유, 생존성 채점 포인트 상실 |

**결정: 예산 모델(45초)** — 이유: `AI_TIMEOUT_SEC`이 "연결·읽기·추가 시도·대기 포함 전체 예산"이라는 정의를 문서와 테스트(test_ai_http_budget)로 고정하고, 타임아웃은 재시도하지 않는다. 변경은 코드 1곳(config 기본값)+문서 3곳(#42)으로 끝나도록 설계돼 있었던 점도 변경 비용을 낮췄다.

## ADR-004. 대화 문맥 전략 ✅ → 직전 N턴 성공 Q/A (CONTEXT_TURNS 0~200, 기본 5)

**배경**: "이전 대화를 기억하는 챗봇"이 과제의 심장(역할카드 07). 토큰 비용과 시연 명확성의 균형이 필요.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **직전 N쌍 Q/A (성공만)** | 구현·설명·검증 단순, 토큰 상한 예측 가능, 실패 로그가 섞여도 문맥 오염 없음 | 먼 과거는 참조 불가 |
| 전체 기록 주입 | 완전한 기억 | 토큰 비용 비선형 증가, 오래된 무관 대화가 응답 품질 저하 |
| 대화 요약 저장 | 비용 절감 | 요약 품질·지연 추가, "원문 인용" 시연이 어려워짐 |
| RAG(벡터 검색) | 장기 기억 | 임베딩·벡터 저장소 인프라 — 과제 범위 밖 |

**결정: N턴 방식** — 이유: 역할카드 07이 "직전 N개 Q/A 포함"을 지정하고, `build_context` 순수 함수로 단위 테스트가 가능하다. 추가 결정: ① **성공(status=success) Q/A만** 포함해 실패 응답이 문맥을 오염시키지 않게, ② UI 복원도 같은 `status=success&limit=N` 계약을 공유해 화면과 AI가 같은 기억을 보게(PR #28), ③ 12번째 요청의 프롬프트 문자량 실측 실험(scripts/experiment_context_turns.py, DEMO_CONTEXT.md)으로 비용 증거까지 확보.

## ADR-005. 이메일 발송 경로 ↻ SMTP → Resend HTTPS API (09-10 변경)

**배경**: 비밀번호 재설정(FR-05) 채택 시 발송 수단이 필요. 초기에는 Gmail SMTP(SMTP_SSL) 경로를 구현.

| 선택지 | 장점 | 단점 |
|---|---|---|
| Gmail SMTP | 무료, 표준 프로토콜 | **Railway Free/Hobby는 SMTP 아웃바운드(25/465/587/2525) 전면 차단** — 09-10 Shell 실측 `OSError: [Errno 101]`로 확인(이슈 #100), 앱 비밀번호 2단계 설정 번거로움 |
| **Resend HTTPS API (443)** | 모든 플랜에서 허용되는 포트, JSON API로 간단 | 외부 서비스 가입·키 관리, 도메인 인증 전 본인 이메일만 수신 |
| SendGrid 등 타 API | 동급 | 무료 한도·가입 절차 유사 — Resend가 가장 단순 |
| 콘솔 출력/링크 직접 노출 | 구현 0 | 보안상 말도 안 됨(토큰이 URL로 누구에게나), 운영 기능 불성립 |

**결정: Resend 우선 + SMTP 폴백 유지** — 이유: `RESEND_API_KEY` 설정 시 Resend, 미설정 시 기존 SMTP(로컬 개발·Pro 대비), 둘 다 없으면 기존 동작(개발=로그 출력, 운영=503). SMTP 코드를 버리지 않은 이유: 로컬 fake 테스트 10건이 무수정으로 통과해 회귀 안전망이 유지됐기 때문(PR #101, 단위테스트 7건 추가, 전체 205 passed). **교훈: 플랫폼 제약은 "설정 문제가 아닌지" 먼저 Shell에서 격리 실측하고(Errno 101), 코드 변경은 우선순위 폴백 구조로 최소화한다.**

## ADR-006. 브랜치 전략·머지 규칙 ✅ → main ← develop ← feature, Merge commit 전용

**배경** (역할카드 02, D1~D2): 과제 요구 "브랜치 전략 + 팀원별 유의미한 커밋 10회+".

| 선택지 | 장점 | 단점 |
|---|---|---|
| **main/develop/feature 3단 + PR 필수 + Merge commit만** | 운영(main)·통합(develop) 분리로 배포 스냅샷이 항상 의미 있음, 개인 커밋이 이력에 그대로 남음 | 머지 커밋이 많아 이력이 복잡, develop 동기화 관리 필요 |
| GitHub Flow (main+feature만) | 단순 | 배포 커밋과 실험 커밋이 섞여 "배포 가능 시점" 식별이 어려움 |
| Trunk-based | 통합 충돌 최소 | 짧은 수명 브랜치 문화가 필요 — 커밋 10회 증빙 요구와 상충 |
| Squash 머지 허용 | 이력 깔끔 | **PR 안의 커밋 N개가 1개로 소멸 → 개인별 커밋 수 증빙 자체가 사라짐** |

**결정: 3단 git-flow 경량 + Squash 금지** — 이유: "커밋 10회" 채점을 머지 시점에 지우지 않는 것이 최우선. 룰셋(`allowed_merge_methods: ["merge"]`, 필수 승인 1, 마지막 push 셀프승인 차단, stale review 해제, 스레드 해결 강제, non_fast_forward/deletion 차단, bypass 없음)을 09-05 적용(#16)하고 저장소 설정으로도 Squash 버튼을 제거해 이중 안전장치를 뒀다(docs/git-rules.md 증빙). 실제 효과: 주간 감사가 `shortlog --no-merges`만으로 가능했고 1주차 0커밋 문제(#45)를 조기 발견했다.

## ADR-007. CI/CD 게이트 구성 ✅

| 선택지 | 장점 | 단점 |
|---|---|---|
| **CI: ruff+black+isort+pytest / CD: 테스트→Secrets 검증→변수 동기화→배포→헬스→스모크** | 스타일·동작·운영 3계층 전부 기계 검증, Secrets 누락 시 "성공으로 표시하지 않고 실패 중단" | 로컬과 CI 포맷 차이로 잦은 재푸시 (black 후속 커밋 발생 — 관행으로 보완) |
| lint만 (테스트 없음) | 빠름 | 회귀를 못 잡음 — #60 사례가 보여주듯 테스트가 없는 영역은 CI로도 못 잡음 |
| 수동 검증 (CI 없음) | 설정 비용 0 | 증빙(녹색 배지·실행 기록) 자체가 채점 요건 |

**결정: 전체 게이트** — 이유: CI 배지·실행 기록이 평가 증빙이고, "CD는 필수 Secrets 없으면 실패"라는 원칙이 "가짜 성공"을 막는 유일한 장치다. CD 게이트 순서는 운영 URL 게시(#83)와 직결됐다.

## ADR-008. 테스트 전략 ✅ → 단위+통합 중심, E2E/브라우저는 선택 증빙

| 선택지 | 장점 | 단점 |
|---|---|---|
| **pytest 단위(스키마·정책·순수함수)+통합(TestClient 실제 흐름) 205건** | 빠른 피드백, CI 게이트 가능, 계약별 회귀 고정 | 프론트 JS·실제 브라우저 렌더링은 미커버 |
| Playwright E2E 필수화 | 실제 화면 검증 | 실행 시간·인프라 비용이 CI마다 발생, 유지보수 부담 |
| 수동 테스트만 | 공수 최소 | #60이 증명한 대로 회귀를 문서로만 막을 수 없음 |

**결정: pytest 중심 + 브라우저 캡처는 스크립트(선택 실행)** — 이유: 백엔드 계약이 과제 채점의 본체다. 프론트 회귀는 ① `test_frontend_contract`(정적 계약 검사)로 최소 방어를 두고 ② Playwright 캡처 스크립트(capture_local_evidence.py)는 증빙 생성용으로 분리했다. 한계 인정: #60 같은 JS 회귀는 CI가 못 잡는다는 사실을 이슈 본문에 명시하고 "머지 직전 develop 재병합 후 삭제 라인 diff 확인"을 PR 절차에 추가했다.
