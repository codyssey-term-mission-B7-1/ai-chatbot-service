## TR-01. HTML 페이지 전면 500 — JSON API만 검사하던 테스트의 사각지대 (09-07)

**증상** (#26): `/`, `/login`, `/signup`, `/logs` 네 페이지가 전부 500. JSON API는 정상이라 기존 테스트가 잡지 못했다.

**원인 분석** (PR #24):
1. `app/routers/pages.py`의 템플릿 경로 계산 오류 — 파일이 `app/routers/` 아래라 `parent.parent`가 `app/`까지만 올라가 존재하지 않는 `app/templates`를 가리킴 (`TemplateNotFound`).
2. `login.html`·`logs.html`에 Jinja2에 없는 JS식 삼항 연산자(`{{ mode == 'signup' ? '회원가입' : '로그인' }}`) 8곳 (`TemplateSyntaxError`).

**해결**: 경로 계산 정정 + Jinja2 문법(`{% if %}`)으로 전면 치환, 4페이지 200 회귀 테스트(`test_pages.py`) 추가.

**교훈**: "HTML 4종 + API 전 경로"를 커버하는 페이지 테스트가 CI 게이트에 들어갔다. **렌더링 계층은 API 테스트로는 절대 검증되지 않는다**는 것을 초기에 배운 사례.

## TR-02. Enter 전송 미구현 → IME 가드 설계 → **머지 회귀**까지 이어진 3막 (09-07)

**1막 — 증상** (#29): 채팅 입력이 `<textarea>`라 Enter가 줄바꿈으로 먹히고 보내기 버튼만 동작. textarea는 암묵적 폼 제출이 없다는 사실을 이슈 본문에서 규명.

**해결** (PR #30): `keydown` 핸들러로 Enter=전송/Shift+Enter=줄바꿈 관례 구현. 이때 **한글 IME 조합 중 Enter(`event.isComposing`)는 전송하지 않는 가드**를 함께 설계 — 한국어 서비스에서 자모 확정 Enter가 전송으로 오인되는 것을 원천 차단.

**2막 — 회귀** (#60, 09-07): PR #43 머지 직후 develop에서 `grep 'Enter|isComposing'`이 0건 — `feature/chat-updates`가 **오래된 분기점 코드를 갖고 와** #30의 커밋을 덮어썼다. 3-way 병합이 파일 단위 수동 충돌 처리에서 보존해 주지 못한 유형. 함께 유입된 것: `innerHTML` 보간 패턴(서버 detail 문자열이 HTML이 되는 위험 구조). `ruff`/`pytest`는 통과 — **JS 테스트가 없어 CI가 못 잡는 회귀**였다.

**해결** (PR #61): Enter/IME 가드 복구, `errorText()` 정규화 후 `textContent` 전용 렌더링, `test_frontend_contract` 정적 계약 검사 도입, PR 체크리스트에 "머지 직전 develop 재병합 → 삭제된 라인 diff 확인" 추가.

**교훈**: ① 기능 추가는 항상 최신 develop 기반으로 rebase 후 진행, ② CI가 못 잡는 영역(JS)에는 최소한의 정적 계약 검사라도 둔다, ③ 회귀는 "보고 → 복구 PR이 바로 뒤따르는" 절차로 즉시 처리.

## TR-03. DB 재생성 후 stale 세션이 다른 계정으로 해석됨 — 조용한 권한 승격 (09-07)

**증상** (#33): DB를 재생성하고 id=1로 다른 계정을 만들면, 예전 쿠키(`user_id=1`)가 **새 id=1 계정으로 200 인증** — 타 계정 대화까지 열람. 에러 로그가 전혀 없는 조용한 오동작.

**원인 분석**:
- 세션 쿠키의 `user_id` 정수를 blind 신뢰.
- SQLite는 AUTOINCREMENT가 아니라 최대 id 기반 재할당 → DB 재생성·삭제 시 id 재사용.
- 세션 해석 경로가 `get_current_user`·`_session_user` 2곳에 중복돼 검증 누락 여지 존재.

**해결** (PR #34): 로그인 시 `user_id`+`email_fp`(이메일 지문) 동시 저장, 해석 시 대조 — 불일치면 세션 파기+401. 해석 로직 단일 함수 통합 + DB 재생성 시나리오 회귀 테스트.

**교훈**: "식별자만 믿는 설계"는 저장소가 id를 재발급하는 순간 무너진다. **세션은 발급 대상과 묶이는 보조 식별자를 반드시 함께 담는다.** 이 원칙은 이후 #54(쿠키 위조) 대응의 토대가 됐다 — 바인딩이 있어도 시크릿이 공개되면 무력하다는 연쇄 분석으로 이어짐.

## TR-04. AI 타임아웃 10초는 너무 짧다 — 기본값 변경과 예산 개념 정리 (09-07)

**증상** (#41): 응답이 조금만 길어져도 504+AI_TIMEOUT. 실사용 불능 수준.

**해결** (PR #42): 기본값 10→45초. 변경 범위를 사전 조사해 **코드 1곳(config)+문서/예시 3곳**으로 확정(테스트는 TimeoutException 주입 방식이라 무관, 프론트는 별도 타임아웃 없음 — 이슈 본문에 근거 명시).

**심화** (PR #43): 네이토 API 실연동 + `AI_TIMEOUT_SEC=0.001` 강제 유발로 504 생존·에러 매핑·`ai_call_fail` 로그를 실측 검증 (역할카드 06 완료 조건 충족).

**교훈**: 기본값 하나도 "영향 범위 조사 → 변경 목록 → 수용 기준"을 이슈에 적는 습관이 리뷰 비용을 줄인다. 타임아웃이 "연결+읽기+재시도 포함 전체 예산"이라는 정의(ADR-003)는 이때 정리됐다.

## TR-05. 보안 전수 감사 — 하루에 발견한 Critical 6건과 일괄 수습 (09-07 → 09-08)

스스로 공격자 관점에서 전수 점검해 이슈 #54~#59를 등록, 09-08에 PR #62·#76~#79로 일괄 수습했다.

### TR-05-1. 공개 기본 SESSION_SECRET으로 쿠키 위조 (Critical, #54)
- **재현**: 코드·.env.example의 기본 시크릿으로 서명된 위조 쿠키로 uid 1/2의 대화 열람·대리 발화 가능. #34의 바인딩 방어도 시크릿을 아는 앞에서는 무력.
- **해결** (PR #62): **부팅 게이트** — 운영(DEBUG=false)에서 공개 기본값·32자 미만이면 `RuntimeError` 기동 거부. 단 **개발은 깨뜨리지 않는다**(경고+임시 키) — 평가자가 .env.example 복사만으로 앱을 띄울 수 있어야 하기 때문. 회귀 테스트 4패턴(약한값+운영=거부 / 약한값+개발=대체 / 강한값=통과 / 위조쿠키=401).

### TR-05-2. 세션 쿠키 문제 3건 (#55 수명·Secure·폐기, #59 email 평문)
- 14일 만료+Secure 없음+서버 폐기 수단 부재 / 페이로드에 email 평문(base64는 암호화가 아님).
- **해결** (PR #78): Max-Age 24시간·환경변수화(1~168h), 운영 Secure, **iat 기반 계정별 세션 전면 폐기 테이블**(`session_revocations`, `scripts/revoke_sessions.py --email`). email은 지문으로 제거.

### TR-05-3. GET limit=-1 무한 조회 (#56)
- SQLite 음수 limit은 무제한 → 200건 상한 우회. **해결**(PR #62): 상한 검증·정규화 + 회귀 테스트.

### TR-05-4. 보안 헤더 전무·운영 /docs 노출·Origin 무검증 (#57, #75)
- **해결**: PR #62에서 nosniff·X-Frame-Options·Referrer-Policy 기본 헤더를 먼저 추가하고, PR #79가 CSP·교차 출처 상태 변경 요청 403(Origin 없는 curl/스모크는 통과)·운영 `DOCS_ENABLED=false`에서 /docs 404를 완성. CSP 적용을 위해 프론트의 인라인 JS를 addEventListener 방식으로 전환한 점이 화면 명세(D-15)와 연결.

### TR-05-5. 로그인 무차별 대입·이메일 열거 타이밍 (#72)
- **실측**: 존재 이메일+오답 ~282ms(bcrypt) vs 미존재 ~12ms — 응답 본문이 같아도 시간으로 회원 열거 가능.
- **해결** (PR #76): 이메일별 실패 잠금(5회/15분, 429+Retry-After) + **미존재 이메일에도 더미 bcrypt 수행**으로 타이밍 평탄화 + `login_fail`/`login_rate_limited` 이벤트(이메일 도메인만 기록).

**교훈**: ① 감사는 "기능이 동작한다"와 "막혀 있다"를 분리해서 본다 — 동작 테스트만으로는 보안 결함이 안 보인다. ② 실측 수치(282ms/12ms, Errno 101)를 이슈에 남겨야 해결의 검증 기준이 된다. ③ 여러 건을 발견해도 **완료 기준을 이슈별로 분리**해 두면 일괄 수습 후에도 검증이 개별적으로 가능하다.

## TR-06. FK cascade가 실제로는 없었다 — ERD 주장과 SQL 현실의 불일치 (09-07)

**증상** (#51): ERD가 주장하는 cascade 삭제가 ORM 경로에서만 성립. `PRAGMA foreign_keys` 미설정이라 SQL 레벨에서는 FK 자체가 미강제.

**해결** (PR #63): SQLite 연결 시 `PRAGMA foreign_keys=ON` 강제 + `ondelete=CASCADE` 정합 확인 + 시드 스크립트 경로 안내 정정(#52)과 `MAX_QUESTION_LENGTH` 실연결(#53, 데드 설정을 schemas·화면까지 전파)을 한 릴리스에 묶어 정정.

**교훈**: **문서(ERD)에 적힌 제약은 DB가 실제 강제하는지 테스트로 증명**해야 한다. "문서와 구현의 불일치"는 기능 부재만이 아니라 "문서만 존재하는 제약"에서도 생긴다.

## TR-07. Railway 배포 실패 "No start command detected" (09-09)

**증상** (#81): CD에서 Railway 빌드 FAILED — 배포 10376f75. 운영이 전면 중단된 상태.

**원인 분석**: Railway가 deprecated된 `railway.json`의 `startCommand`를 무시하고 신규 빌더(Railpack v0.39) 자동 감지로 전환 — `app/main.py` 구조는 감지 규칙에 없음.

**해결**: Nixpacks/Railpack 공통 인식 `Procfile`(`web: uvicorn app.main:app --host 0.0.0.0 --port $PORT`)을 루트 추가. `railway.json`은 헬스체크/재시작 정책 의도 문서로 유지. 긴급 머지는 CONTRIBUTING의 관리자 예외 절차(사전 승인·즉시 보호 복구)를 따랐고, 병합 후 develop→main 릴리스 PR + CD 재실행으로 배포 성공 검증 → 같은 날 운영 URL 게시(#83)까지 완료.

**교훈**: PaaS의 빌더 동작은 **언제든 바뀐다**. 시작 명령은 플랫폼 문서가 아닌 저장소의 파일(Procfile)이 단일 진실 원본이 되게 하고, 배포 관련 변경은 앱 코드와 분리해 원인 특정을 쉽게 했다.

## TR-08. Railway Free/Hobby SMTP 아웃바운드 차단 — 발송 경로 재설계 (09-10)

**증상** (#100): 운영에서 비밀번호 재설정 메일이 발송되지 않음(502). 로컬에서는 잘 동작했다.

**원인 격리 실측**: Railway Shell에서 `smtplib.SMTP_SSL("smtp.gmail.com", 465)` → `OSError: [Errno 101] Network is unreachable`. Gmail/Naver 무관, **플랜 자체가 SMTP 포트(25/465/587/2525)를 차단**(공식 문서·스태프 답변 확인) — 설정 값 문제가 아님을 먼저 증명.

**해결** (PR #101): **Resend HTTPS API(443) 경로 추가 + 우선순위 폴백**: `RESEND_API_KEY` 있으면 Resend → 없으면 기존 SMTP(로컬·Pro 대비) → 둘 다 없으면 기존 동작(개발=로그 출력, 운영=503). 실패 시 기존 502 경로 재사용(키·원문 노출 없이 상태코드만 로그). SMTP 테스트 10건 무수정 통과 + 신규 단위테스트 7건, 전체 205 passed. 운영 절차(가입→키 발급→Secrets→CD→1회 발송 테스트, 요청 상한 15분/3회 주의)까지 런북화.

**교훈**: ① 네트워크 오류는 **코드 밖(플랫폼 제약)과 안(버그)을 Shell 실측으로 먼저 분리**한다. ② 재설계는 폴백 구조로 기존 경로를 살려 회귀 안전망을 유지한다. ③ 발급→등록→검증 절차서가 없으면 해결 코드는 운영 성공과 다시 갈라진다.

## TR-09. CI만 실패하는 초 경계 flake (09-09)

**증상** (#98): 동일 커밋인데 push 실행에서만 `test_revoke_by_email_normalizes_case` 실패(`assert False is True`), PR 실행은 통과.

**원인 분석**: 폐기 전후로 `int(time.time())`을 두 번 호출하는 테스트 코드가 초 경계를 넘기면 `iat = epoch+1`이 되어 `iat <= epoch` 판정이 뒤집힌다. 앱 코드에는 #78 교훈의 유사 경합 대응이 이미 있었지만 **테스트가 같은 실수를 반복**했다.

**해결** (PR #99): 폐기 전 시각을 `iat`으로 사용하는 결정적 단언으로 수정, 동일 파일 유사 패턴 점검.

**교훈**: 시간 기반 테스트는 "실제 now를 두 번 부르지 않는다" — 기대값을 사전에 고정해야 경계에서 flake가 사라진다. flake는 원인 불명 채로 재실행하지 않고 반드시 원인 확정 문서를 남긴다.

## TR-10. 문서·이력 불일치 전수 감사 (09-07)

**증상**: 일괄 감사에서 다수 발견 — #46(기본 브랜치 main에 앱 코드 0건), #47(README 개인별 요약이 빈 플레이스홀더), #48(로그 이벤트 종수가 README 6종/CONTRIBUTING 8종/실제 11종 3중 불일치), #49(감사 수치 미갱신), #50(TODO 사실 오류 2건: max_age '미설정'은 실제 14일, Enter 전송 '미완료'는 이미 머지됨).

**해결** (PR #63·#64·#66 등): 사실 오류 정정 → develop→main 릴리스로 기본 브랜치 정합화 → "이후 문서 수치는 실측 명령(shortlog 등)과 함께 기록" 규칙화. 이후 감사 기록 갱신(#96)과 "stale 사실 정정"(배포 상태·세션 수명 등)을 상시 운영.

**교훈**: 문서 불일치는 악의가 아니라 **갱신 규칙 부재**에서 온다. "수치는 명령 재현과 함께, 상태 표기는 날짜와 함께"를 컨벤션으로 박제했고, TODO.md에는 "과거 기록을 새 코드의 승인/검증인 것처럼 바꾸지 않는다"는 원칙이 남았다.

## TR-11. 데모 모드를 실연결로 표시하는 오류 (09-07)

**증상** (#58): `AI_API_KEY`가 **빈 문자열**이면 /health·화면 배너가 '실연결'처럼 표시 — Fake 응답인데도 데모가 아닌 것처럼 보임.

**해결**: 키 유효성 판정을 "값 존재"로 엄밀히 하고 `ai_mode`(real/demo)를 /health로 공개, UI 배너·README·M3 증빙이 같은 근거를 공유. 실 AI 검증은 `scripts/ai_check.py --require-real`(키 없으면 종료 2, 성공으로 위장 안 함)로 별도 수행.

**교훈**: "동작한다"와 "진짜다"의 경계가 채점 신뢰성의 핵심 — **증빙의 등급(로컬/Fake/모의 HTTP/운영 실AI)을 문서가 항상 자기표시**해야 한다.
