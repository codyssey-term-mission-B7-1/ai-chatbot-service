## 1. 배경과 문제 정의

과제 요구는 "웹 기반 AI 챗봇 서비스"다. 팀은 과제 문장에서 출발해 다음과 같이 문제를 정의했다 (README §1과 동일하게 유지).

| 항목 | 내용 |
|---|---|
| 문제 | 질문·답변이 흩어지면 이전 대화의 맥락과 개인 기록을 다시 확인하기 어렵다. |
| 대상 | 계정별 질의응답·자신의 대화 기록을 추적하려는 사용자 |
| 핵심 흐름 | 가입 → 로그인 → 질문 → AI 응답 → 성공 대화 문맥 유지 → 본인 기록 조회 · 비밀번호 재설정(이메일 링크) |
| 운영자 흐름 | 명시적으로 권한을 부여받은 관리자 계정만 전체 기록 조회·필터 가능 |

**해결 가치 3가지**
1. **문맥 유지** — 같은 사용자의 직전 성공 Q/A를 프롬프트에 포함해 연속 대화가 자연스럽다 ("내가 방금 뭘 물어봤지?" 시연).
2. **기록 소유** — 모든 질문·응답이 사용자별로 저장되고, 본인만 조회한다.
3. **운영 가능성** — 타임아웃에도 서버가 죽지 않고, 로그로 추적하며, 배포 URL이 평가 시점에 살아 있다.

## 2. 목표와 성공 기준

| 구분 | 기준 | 측정 방법 |
|---|---|---|
| 기능 | 가입→로그인→질문→응답→기록 조회 전 흐름 동작 | 통합 테스트 + 수동 시나리오 |
| 안정성 | AI 타임아웃·오류에서도 서버 생존, 오류 코드로 안내 | `AI_TIMEOUT_SEC=0.001` 강제 유발 → 504 캡처 |
| 협업 | 팀원별 유의미한 커밋 10회 이상, PR 기반 병합 | `git shortlog -sne --no-merges` 주간 감사 |
| 운영 | 외부 접속 가능한 URL 상시 가동 | Railway 배포 + E2E 스모크 스크립트 |
| 문서 | 문서·Git·코드·배포 4자 일치 | M3 제출 점검표 31항목 대조 |

평가 기준(사전평가 31항목)을 D-day 역산으로 뒤집어 보면, "문서와 실제 구현의 불일치"가 최대 감점 요인이므로 **문서를 나중에 몰아 쓰지 않고 구현과 함께 갱신**하는 것을 원칙으로 삼았다.

## 3. 타깃 사용자와 페르소나

| | 페르소나 A — 학습자 "민수" | 페르소나 B — 운영자 "운영" |
|---|---|---|
| 특성 | 질문을 여러 번 이어서 하고, 예전에 물어본 내용을 다시 보고 싶다 | 서비스 전체 사용 현황을 점검해야 한다 |
| 니즈 | 문맥이 이어지는 응답, 내 기록만 볼 수 있는 화면 | 전체 대화 로그 조회·필터, 계정 관리 |
| 사용 화면 | /signup, /login, /(채팅), /logs | /admin/logs (+ manage_admin.py) |

## 4. 핵심 사용자 시나리오

1. **가입/로그인**: 이메일+비밀번호(8~64자)로 가입 → 서명된 세션 쿠키 발급 → 로그인 상태에서만 채팅·기록 접근.
2. **문맥 대화**: "나를 기억해?" → "방금 뭐라고 물었지?" 연속 질문에서 직전 Q/A가 프롬프트에 포함되어 AI가 이전 질문을 인용.
3. **기록 복원**: 새 브라우저로 재접속해도 서버가 저장한 성공 대화 N개가 같은 범위로 복원된다 (`status=success&limit=N`).
4. **오류 상황**: AI가 느리면 45초 예산 후 504 + "AI 응답이 지연되고 있어요" 안내 — 서버는 생존, 사용자는 다시 시도 가능.
5. **비밀번호 분실**: 이메일로 재설정 링크 수신 → 토큰 단일 사용 → 완료 시 기존 세션 전면 폐기. *(09-09 확장 채택 — §7 D-04)*
6. **운영자 조회**: `manage_admin.py`로 명시 부여된 계정만 /admin/logs에서 전체 기록·필터 조회.

## 5. 제품 범위 (Scope)

**In (구현 대상)** — 역할카드 13개에 분해된 범위:

| 영역 | 내용 | 담당 카드 |
|---|---|---|
| 서버 기반 | FastAPI 구조, 설정, /health | 03 |
| 회원 인증 | 가입/로그인/로그아웃/내정보, bcrypt | 04 |
| 접근 제어 | 비로그인 401·HTML 302, 타인 기록 차단 | 05 |
| AI 연동 | OpenAI 호환(네이토) httpx 클라이언트, 타임아웃/재시도 | 06 |
| 챗 파이프라인 | 문맥 빌더 + 질문→AI→저장 흐름 | 07 |
| DB | users/chat_logs, 개인 기록 조회 | 08 |
| UI | 채팅/인증/기록 화면 | 09·10 |
| 로깅·검증 | 표준 이벤트, Pydantic 검증 | 11 |
| 배포/운영 | Railway, 환경변수, 스모크 | 12 |
| 문서/증빙 | API 명세, ERD, 증빙 패키지 | 13 |

**Out (의도적으로 제외 — 과제 범위 밖이거나 비용 대비 효과 없음)**
- 실시간 스트리밍 응답(SSE/WebSocket) — 표준 파이프라인 검증이 우선
- 소셜 로그인/OAuth — 과제 요구는 이메일 기반 인증
- 다중 워커/수평 확장 — 단일 uvicorn 프로세스 전제 (메모리 rate limiter의 한계를 문서에 명시)
- 대화 요약·RAG 검색 — 문맥은 "직전 N턴"으로 충분 (ADR-004)

## 7. 기획 단위 의사결정 기록

### D-01. 제품 콘셉트 — 무엇을 만들 것인가

| 선택지 | 장점 | 단점·비용 |
|---|---|---|
| **(1) 로그인형 챗봇 + 대화 저장/문맥에 기능 집중** | 과제 필수 흐름 그대로, 검증 가능한 범위, 13개 역할카드가 1:1 분해됨 | 화려한 부가기능이 없어 차별성이 낮아 보임 |
| (2) 다기능 범용 챗봇 (모델 선택·파일 업로드·플러그인 등) | 데모 임팩트가 큼 | 15일 D-day에 검증 불가능한 범위 → "문서와 실제 불일치" 감점 위험 최대 |
| (3) 관리자/분석 콘솔 중심 (대시보드·통계) | 차별화 가능 | 과제 핵심(사용자 챗봇 흐름)이 옅어짐, 관리자 기능은 이미 보조 범위로 충분 |

**최종 선택: (1)** — 이유: 채점 기준이 "기본 흐름의 실제 동작 + 문서·Git·배포 일치"에 있다. 15일 안에 (2)는 검증 불가능하고, (3)은 핵심을 희석한다. 기능을 줄이되 **각 기능의 오류 상황까지 검증**(타임아웃 생존, 권한 차단)하는 것을 차별점으로 택했다. 실제로 이 선택 덕분에 테스트 205개가 기능 명세 1:1로 붙었다.

### D-02. 사용자 식별 방식

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(1) 이메일+비밀번호 계정제** | 과제 요구(가입/로그인/개인 기록) 정합, 구현·검증 명확 | 비밀번호 보안 책임(해시·재설정)이 생김 |
| (2) 익명 세션(디바이스 식별) | 가입 마찰 없음 | "회원 인증" 채점 항목 자체를 만족 못함, 기기 변경 시 기록 상실 |
| (3) 소셜 로그인(OAuth) | UX 좋음, 비밀번호 책임 회피 | 외부 앱 심사·리다이렉트 설정이 배포 병목, 과제 요구와 불일치 |

**최종 선택: (1)** — 이유: 과제 필수 요구사항의 핵심이고, 개인 기록 소유라는 해결 가치와 직결. 비밀번호 보안 책임은 bcrypt+페퍼와 이메일 재설정으로 정면 대응하기로 했다(03-기능명세서 D-10).

### D-04. 범위 조정 사례 — 비밀번호 재설정의 채택 (09-09 결정)

초안(08-30)에서는 비밀번호 재설정을 Out으로 두었다(이메일 인프라 비용). 그러나 ① 운영 관점에서 잠긴 계정이 복구 불가능한 결함이고, ② SMTP 대신 콘솔 출력 폴백으로 로컬 검증이 가능하며, ③ M1 잔여 여유가 확인되어 **09-09 In으로 재편**(PR #86/#88, 이후 #101 Resend 경로). 반대로 "대화 요약/RAG"는 계속 Out 유지 — 문맥 시연이 N턴으로 충분히 검증됐기 때문.

> **교훈**: 범위 문서는 한 번 쓰고 끝이 아니라, 마일스톤 경계마다 In/Out을 다시 심사한다. 채택·제외 이유를 같이 기록해야 감사 대조 시 "문서 불일치"가 되지 않는다.
