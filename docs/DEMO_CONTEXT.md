# 문맥 유지 시연 증빙 (#7)

> 완료 조건: **연속 3질문 이상에서 문맥 유지 시연 성공**
> 재현 스크립트: `scripts/demo_context.sh` · 실행일: 2026-09-07

## 1. 무엇을 검증하는가

`POST /api/chat`은 매 요청마다 같은 사용자의 **직전 N개(`CONTEXT_TURNS`, 기본 5) Q/A**를
프롬프트에 실어 AI에 보낸다 (`app/services/context.py:build_context`).

3턴째에 "내가 방금 뭘 물어봤지?"를 물었을 때 **2턴째 질문이 응답에 인용되면**
컨텍스트가 실제로 전달된 것이다. 스크립트는 이 인용 여부를 검사해
없으면 종료코드 1로 실패한다 — 눈으로 보는 시연이 아니라 자동 검증이다.

## 2. 재현 방법

```bash
# 1) 목업 AI 서버 (실제 키 없이 검증 — 네이토 OpenAI 호환 시뮬레이터)
python scripts/mock_openai_server.py          # :8001

# 2) .env 를 목업으로 연결
#    AI_API_KEY=mock-key / AI_BASE_URL=http://127.0.0.1:8001/v1 / AI_MODEL=neito-1

# 3) 앱 서버
uvicorn app.main:app --port 8000

# 4) 시연
./scripts/demo_context.sh http://127.0.0.1:8000
```

> 실제 네이토 키가 준비되면 `.env`의 `AI_BASE_URL`/`AI_MODEL`/`AI_API_KEY`만 바꿔
> 같은 스크립트를 그대로 돌리면 된다 (카드 #6).

**핵심 근거 2가지**

1. 목업이 보고한 **컨텍스트 반영 건수가 0 → 1로 누적** — 턴이 쌓일수록 프롬프트에 과거 Q/A가 더 실린다.
2. 3턴째 응답이 **2턴째 질문 문자열을 그대로 인용** — 컨텍스트 없이는 불가능한 응답.

## 4. 서버 로그 이벤트 (파이프라인 추적)

`request_id`로 한 요청의 전 구간을 추적할 수 있다.

```
event=request_received  user_id=1 path=/api/chat request_id=567fc45c question=환경변수는 뭐가 필요해?
event=ai_call_start     user_id=1 request_id=567fc45c
event=ai_call_success   request_id=567fc45c latency_ms=5
event=db_save_success   user_id=1 chat_id=2 status=success
```

3턴 전체가 동일한 순서로 기록되며, 질문은 로그 컨벤션대로 50자에서 잘린다.

# CONTEXT_TURNS 값 실험 (#7)

> 카드 #7 TODO: "`CONTEXT_TURNS` 값 실험 (3/5/10 — 토큰 비용 vs 문맥 품질)"
> 재현: `python scripts/experiment_context_turns.py`

## 1. 측정 방법

실제 `/api/chat` 파이프라인을 그대로 태우고, AI 프로바이더에 전달된 `messages`를 가로채
프롬프트 크기와 문맥 커버리지를 잰다. 추정이 아니라 **실제 전송되는 프롬프트**를 측정한다.

- 12턴 대화를 쌓은 뒤 마지막(13번째) 요청의 프롬프트를 분석
- 답변 길이는 300자로 고정 — 실제 AI 응답 길이에 가깝게 맞춰 프롬프트 크기를 현실화
- 인메모리 SQLite + 캡처용 페이크 프로바이더 (AI 실호출 없음, `CONTRIBUTING.md` 규칙 준수)

## 2. 결과

```
  N      메시지 수    과거 Q/A        프롬프트 문자        가장 오래된 턴
-------------------------------------------------------
  3          8         3          1,131               9번째
  5         12         5          1,749               7번째
 10         22        10          3,294               2번째
```

| N | 프롬프트 문자 | N=3 대비 | 기억하는 범위 |
|---:|---:|---:|---|
| 3 | 1,131 | 1.0배 | 직전 3턴 |
| **5 (현재 기본값)** | **1,749** | **1.5배** | **직전 5턴** |
| 10 | 3,294 | 2.9배 | 직전 10턴 |

프롬프트 크기는 N에 거의 **선형으로 증가**한다 (턴당 약 +310자 ≒ 질문 + 300자 답변).
AI API 요금은 입력 토큰에 비례하므로, **N을 2배로 늘리면 매 요청 비용도 대략 2배**가 된다.

## 3. 결론 — 기본값 5 유지

| 후보 | 판단 |
|---|---|
| N=3 | 가장 싸지만 3턴 전 내용을 이미 잊는다. 짧은 문답 두세 번이면 문맥이 끊긴다. |
| **N=5** | **채택.** N=3 대비 1.5배 비용으로 문맥 2턴을 더 확보. 일반적인 대화 흐름을 덮는다. |
| N=10 | 2.9배 비용. 실사용에서 10턴 전을 다시 참조하는 경우는 드물어 비용 대비 이득이 낮다. |

**타임아웃 제약이 추가 근거다.** 이 서비스는 `AI_TIMEOUT_SEC=10`으로 응답을 강제 종료한다.
프롬프트가 길수록 AI 응답 지연이 커지므로, N을 키우면 타임아웃(504) 발생 확률도 함께 올라간다.
비용과 안정성 양쪽에서 5가 합리적인 지점이다.

> 값은 코드에 박혀 있지 않다. `.env`의 `CONTEXT_TURNS`로 조절하며,
> 실제 네이토 모델의 응답 길이와 요금이 확인되면(카드 #6) 이 실험을 다시 돌려 재조정한다.

## 4. 실험에서 드러난 한계와 대응

N턴을 넘어가는 과거 대화는 프롬프트에 **아예 포함되지 않는다.** 이때 AI가 모른다고 답하지 않고
그럴듯하게 지어내면 사용자는 챗봇이 거짓말한다고 느낀다.

→ 시스템 프롬프트(`app/services/context.py`)에 두 줄을 추가했다.

- 이전 질문은 **사용자가 쓴 표현 그대로 따옴표로 인용**할 것 — 인용 정확도를 높여 시연 검증과도 맞춘다
- **전달된 대화 기록에 없는 내용은 지어내지 말고** 기억나지 않는다고 솔직히 답할 것
