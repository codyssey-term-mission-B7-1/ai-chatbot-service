# 볼륨·디스크 관리 정책 (Volume & Disk Management Policy)

> 작성: giyeop-cody (#3 #12) — 배포 시 카드 12 담당이 적용

## 1. 현재 저장소 구성

| 대상 | 위치 | 증가 요인 | 성장 속도(추정) |
|------|------|-----------|-----------------|
| SQLite DB | `./app.db` (단일 파일) | chat_logs 행 추가 | 질문 1건 ≈ 1~2KB → 1만 대화 ≈ 20MB (과제 기간 과소) |
| 서버 로그 | stdout (현재) | 요청당 수 행 | 분량 크지 않으나 **무한 증가 후보 1순위** |
| 백업본 | `backups/app_*.db` | 매일 1개 × 세대 | 7세대 상한으로 제한 (백업 정책 문서) |
| 업로드 파일 | 없음 | — | 이 서비스는 파일 업로드 미지원 (정책상 유지) |

## 2. 배포 환경 필수 규칙 (가장 흔한 사고 방지)

1. **DB 파일은 영구 볼륨에** — 컨테이너/인스턴스 재시작 시 로컬 디스크는 초기화되는 플랫폼이 많음
   - Render: Persistent Disk 마운트 / Cloudtype: 저장소 바인딩 / AWS: EBS
   - 환경변수 `DATABASE_URL=sqlite:////mnt/data/app.db` 처럼 **볼륨 경로를 가리키도록** 설정
   - ❌ 기본 `./app.db` 그대로 두면 "배포가 되었는데 회원가입이 매일 사라짐" 사고 발생
2. **백업 디렉터리도 같은 볼륨** + 주간 로컬 다운로드 (백업 정책 3-2-1 축약판)
3. ** ephemeral 디스크에 쓰는 것 허용**: `.pytest_cache`, `__pycache__` 등 캐시만

## 3. 용량 관리 (한도·정리)

| 항목 | 한도/주기 | 동작 |
|------|-----------|------|
| DB 크기 | 경고 100MB / 위험 500MB | 위험 시 아카이브 검토 (아래) |
| 백업 세대 | 7개 | 초과분 자동 삭제 (backup_db.sh) |
| 로그 | RotatingFileHandler **10MB × 5백업** (전환 시) | stdout-only 현재는 플랫폼 로그 사용 |
| 오래된 대화 로그 | 보존 정책: **삭제하지 않음**(과제 데이터) | 상용 시: 90일 후 백업본으로 이관하는 아카이브 정책 권장 |

### 용량 점검 (월 1회 + M2/M3)
```bash
du -h app.db backups/ | sort -h
sqlite3 app.db "SELECT COUNT(*), strftime('%Y-%m', created_at) FROM chat_logs GROUP BY 2;"
```

## 4. 로그 저장소 전환 계획 (카드 11과 협업)

현재: stdout → 배포 플랫폼이 수집. 필요 시(증빙·장기 보관) `logging.handlers.RotatingFileHandler`로 전환:
- 경로: 볼륨 내 `/mnt/data/logs/app.log` (10MB×5)
- 전환은 별도 이슈로 — 현재는 플랫폼 로그로 충분 (트레이드오프: 파일 전환 시 로그 조회 API/화면 없이는 원격 열람이 불편해짐 → 플랫폼 콘솔 유지가 이득)

## 5. 트레이드오프
- **SQLite 파일 유지 vs 외부 DB**: 단일 파일=백업·이동·증빙이 쉬움. 동시 쓰기 한계는 4인 과제 트래픽에 무관 → 유지
- **삭제 없는 보존**: 평가 증빙 가치 > 용량 비용 (20MB/만건) — 상용 시에만 아카이브 도입
- **업로드 미지원 유지**: 볼륨 관리 복잡도를 결정적으로 낮춤 (기능 요구에도 없음)
