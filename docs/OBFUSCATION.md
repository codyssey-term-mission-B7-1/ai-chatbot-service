# 난독화 및 코드 보호 정책 (Obfuscation & Code Protection Policy)

> 작성: giyeop-cody (#3) — 결론: **이 프로젝트에서 '난독화'는 선택하지 않고, 대안 전략으로 보호한다**

## 1. 결정: 난독화 미적용 및 그 이유

| 대상 | 결정 | 이유 |
|------|:---:|------|
| 서버 Python 코드 (app/) | ❌ 미적용 | ① 공개 레포(MIT 라이선스) — 난독화와 모순 ② 평가자가 코드를 읽어야 채점 ③ pyarmor 등 도입 비용·디버깅 손해 > 이득 |
| 프론트 JS (static/js) | ❌ 미적용 (minify는 허용) | 파일 1개·난독화할 민감 로직 없음. 배포 시 웹서버 압축(gzip)만으로 충분. 난독화하면 팀원 디버깅만 어려워짐 |
| 설정/키 | ❌ (원천 불필요) | 코드에 키가 없음 → 난독화로 지킬 대상 자체가 없음 (.env 분리 원칙) |

**핵심 원칙: 난독화는 '클라이언트에 전달되는 코드'에만 의미가 있다. 이 서비스의 모든 민감 로직(AI 호출·키·인증)은 서버에만 존재한다.**

## 2. 실제 적용하는 보호 전략 (난독화 대체)

1. **시크릿 격리**: API 키는 `.env`/플랫폼 시크릿만 — 빌드 산출물·레포·프론트 어디에도 미포함
2. **AI 키 서버 사이드 프록시**: 브라우저는 우리 서버만 호출 (`/api/chat`), AI 제공사 키는 브라우저에 도달하지 않음 — 난독화보다 강력한 보호
3. **응답 최소화**: 프론트로 내려가는 JSON은 본인 데이터만 (다른 사용자 데이터·내부 식별자 최소화)
4. **세션 쿠키 서명**: 클라이언트가 위조할 수 없는 서명 쿠키 (itsdangerous)
5. **에러 메시지 무해화**: 500 응답에 스택트레이스 노출 금지 (로그에만 기록) — 구조 힌트 방지
6. **.gitignore로 산출물 관리**: `.env`, `*.db` 등 비공개 파일의 우발적 공개 차단

## 3. 추후 상용 전환 시 (레벨 업 경로)

| 단계 | 조치 |
|------|------|
| 공개→비공개 전환 | 레포 private화 (가장 확실한 '소스 보호' — 난독화보다 우선) |
| 프론트 빌드 도입 시 | 번들러 minify + **소스맵 미배포** (source map은 내부 보관) |
| 라이선스 혼합 시 | 오픈소스/독점 분리 + 독점 모듈만 사내 패키지(사내 전용 패키지 레지스트리)로 |
| 클라이언트 로직 보호 필요 시 | 민감 계산을 서버 API로 이동 (난독화 대신 신뢰 경계 재설계) |

## 4. 트레이드오프
- **난독화 포기** → 평가 가독성·협업 효율·디버깅 속도 획득. '코드 도난' 리스크는 공개 레포 정책과 함께 수용 (과제 성격상 이득이 압도)
- **minify도 기본 미적용** → 정적 파일 1개라 이득 미미. gzip으로 전송 크기는 해결
- 단, **"난독화 안 하면 키가 새는 구조"는 허용하지 않음** — 그 구조 자체를 금지하는 게 이 정책의 본체
